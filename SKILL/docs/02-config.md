# 02. Конфигурация: конфиги, атрибуты, алиасы, единицы, форматы

Этап после создания точки данных: записать значение в конкретный конфиг, создать
конфиг, описать элемент. Начало — [01-create.md](01-create.md), чтение —
[03-read.md](03-read.md).

## dpSet()

**Синопсис**

```c
int dpSet(string dp1, <type1> var1 [, string dp2, <type2> var2, ...]);
int dpSet(dyn_string dpnames, dyn_anytype values);
```

**Назначение.** Присваивает значения атрибутам точек данных. Попутно **создаёт и
удаляет конфиги**. Это основная пишущая функция.

**Параметры**

| Имя | Тип CTRL | Обяз. | Описание | Значение для примера |
| --- | --- | --- | --- | --- |
| `dp1`, `dp2`, … | `string` | да | Атрибут точки данных или её имя | `"Valve17.opening:_original.._value"` |
| `var1`, `var2`, … | любой | да | Присваиваемое значение. Тип определяется атрибутом | `40` |
| — | — | — | Либо `DPCONFIG_DEFAULTVALUE` | `DPCONFIG_DEFAULTVALUE` |
| `dpnames` | `dyn_string` | форма 2 | Массив идентификаторов | `makeDynString("test1.:...","test2.:...")` |
| `values` | `dyn_anytype` | форма 2 | Массив значений. **Длины массивов должны совпадать** | `makeDynBool(false,false)` |

**Возврат.** Обычно `0`, при сбое `-1`.

**Если конфиг/атрибут не указаны, подставляется:**

| Функция | Подстановка |
| --- | --- |
| `dpSet*()` | `_original.._value` |

**Предусловия.** Точка данных и элемент существуют; атрибут принадлежит типу DPE.

**Побочные эффекты.** Записывает значение. Генерирует событие изменения → вызываются
колбэки `dpConnect()`. **Не ждёт** выполнения колбэков. При записи конфига драйвера
может уйти команда в PLC.

**Ожидание.** Неблокирующая.

### Создание и удаление конфигов

Через атрибут `_type` соответствующей константой:

```c
dpSet("Valve17.opening:_default.._type", DPCONFIG_DEFAULTVALUE);  // создать _default
dpSet("Valve17.opening:_default.._type", DPCONFIG_NONE);          // удалить _default
```

### Что писать в примерах

```c
int rc = dpSet("Valve17.opening:_original.._value", 40);
```

**Ошибки.** Через `getLastError()`. Алерты при несуществующих точках данных, ошибках
передачи параметров и опечатках. **При выходе за диапазон исключений нет и ошибок
нет** — тихо.

### Атомарность

Включается конфиг-элементом `atomicDpSet` в секции `general`:
`atomicDpSet = 1` → все операции записи в `_original`, `_lock`, `_general`
атомарны: сначала проверяется, что ни одна запись не провалится, потом применяются
все. Иначе возможна частичная запись. Записи от драйверов WinCC OA **никогда** не
атомарны. По умолчанию выключено.

### Измерено на стенде — 19 проверок, ✅ проверено

* Атрибут не указан → пишется `_original.._value`. Подтверждено чтением.
* Несколько пар в одном вызове применяются все, `rc = 0`.
* Форма `dyn_string` + `dyn_anytype` работает. При несовпадении длин — `rc = -1`
  и `number of items in DP & value list mismatch`.
* **Повтор одного атрибута в одном вызове: принимается ПЕРВОЕ значение**,
  второе отбрасывается, `rc = 0`. Ошибки нет.
* **Несоответствие типа значения ошибки не даёт.** `float 3.9`, записанный в
  int-атрибут, молча превращается в `3`, `rc = 0`. Исключения не бросаются.
* Создание и удаление конфига отрабатывают: `DPCONFIG_DEFAULTVALUE` → `rc = 0`,
  `DPCONFIG_NONE` → `rc = 0`.

**Признак существования конфига — `_type`, а не `_stime`.** У `_default` всего
четыре атрибута и `_stime` среди них нет, поэтому чтение `_default.._stime` даёт
`rc = -1`. Подробности в разделе `dpGetAllAttributes()`.

**Скрипт.** `examples/02-config/01_dpSet.ctl` ✅ проверено, 19/19

**Типичные ошибки**

* **Один вызов — одна система.** Точки данных разных систем в одном `dpSet()`
  не работают:
  `PARAM,SEVERE, 175, this request cannot address more than one system, ...`
* **Повтор атрибута.** Дважды присвоить одному атрибуту в одном вызове нельзя —
  принимается первое, остальные отбрасываются, возврат `0`.
* **Несовпадение длин массивов** в форме `dyn_string`/`dyn_anytype`.
* **Рост времени обработки** нелинейный при большом числе пар.
* Забыть про несоответствие типа значения атрибуту.

## dpSetWait()

**Синопсис**

```c
int dpSetWait(string dp1, <type1> var1 [, string dp2, <type2> var2, ...]);
int dpSetWait(dyn_string dpnames, dyn_anytype values);
```

**Назначение.** То же, что `dpSet()`, но **блокирует** выполнение скрипта до ответа
Event Manager.

**Параметры / возврат / ошибки.** Идентичны `dpSet()`.

**Подстановка по умолчанию:** `_original.._value`.

**Побочные эффекты.** Те же, что у `dpSet()`.

**Ожидание.** **Blocking** (Waiting Control function).

> `dpSetWait()` ждёт ответа Event Manager, но **не** ждёт выполнения колбэков,
> подписанных через `dpConnect()` на изменение этого атрибута.

В распределённой установке ждёт ответ Event Manager **другой** системы; ответ идёт
обратно через dist manager и Event Manager первой системы.

```c
int rc = dpSetWait("Valve17.opening:_default.._type", DPCONFIG_DEFAULTVALUE);
DebugN(rc);
if (dynlen(getLastError()) > 0) { /* обработка ошибки */ }
```

### Измерено на стенде — 16 проверок, ✅ проверено

* Значение видно **сразу** после возврата, без `delay()` — блокирующее
  поведение подтверждено.
* На этом стенде `dpSet()` тоже отдаёт значение сразу: Event Manager отвечает
  быстро. То есть **наблюдаемой разницы по времени между `dpSet()` и
  `dpSetWait()` на практике нет**. Различие в гарантии ожидания ответа, а не в
  измеримой задержке. Полагаться на «подожду на всякий случай `delay()`» после
  `dpSetWait()` смысла не имеет.
* Остальное поведение совпадает с `dpSet()`: первый повторный атрибут,
  несуществующая точка → `rc = -1`, работа с конфигами.

**Скрипт.** `examples/02-config/02_dpSetWait.ctl` ✅ проверено, 16/16

**Типичные ошибки**

* Разные системы в одном вызове — тот же `PARAM, SEVERE, 175`.
* Нет Event Manager → скрипт висит.
* Считать `dpSetWait()` аналогом подтверждения записи значения в PLC — это не так,
  он ждёт только ответ Event Manager.

## dpSetTimed()

**Синопсис**

```c
int dpSetTimed(time t, string dp1, <type1> val1 [, string dp2, <type2> val2, ...]);
int dpSetTimed(time t, dyn_string dpnames, dyn_anytype values);
```

**Назначение.** Пишет значение **с заданным временем источника** (`source time`) в
изменяемые пользователем атрибуты конфига `_original` либо в `_corr.._value`.

**Параметры**

| Имя | Тип CTRL | Обяз. | Описание | Значение для примера |
| --- | --- | --- | --- | --- |
| `t` | `time` | да | Время источника. **Не может быть раньше 1.1.1970 0:00 UTC** | `makeTime(1996,3,5,12,30)` |
| `dp1`, … | `string` | да | Атрибуты `_original` | `"valve17.opening:_corr.._value"` |
| `val1`, … | любой | да | Значения | `40.0` |

**Возврат.** Обычно `0`, при сбое `-1`. Ошибки — `getLastError()`.

**Что можно писать.** Только атрибуты, изменяемые пользователем:
`_value`, `_active`, `_exp_default`, `_exp_inv`, `_per_active`, а также
пользовательские биты `_userbit1`…`_userbit8`. Плюс отдельно — `_corr.._value`.

**Про историю.** История конфигов тревог, у которых время задано `0`, **не
сохраняется**; последнее значение всё же лежит в базе. Чтобы не раздувать историю
конфигурации, время конфигов `_alert_hdl` и `_alert_class` можно задавать через
`dpSetTimed(0, ...)`; для остальных конфигов `dpSetTimed(0, ...)` не нужен и не
поддерживается.

```c
dpSetTimed(makeTime(1996,3,5,12,30), "valve17.opening:_corr.._value", 40.);
```

**Ожидание.** Неблокирующая (в отличие от `dpSetTimedWait()`).

### Измерено на стенде — 22 проверки, ✅ проверено

**Главный вывод: код возврата не является признаком успеха.**
`dpSetTimed()` возвращает `0` практически всегда — и когда запись прошла, и
когда проигнорирована, и когда атрибут менять запрещено. `getLastError()` при
этом тоже пуст. Проверять результат можно **только чтением обратно**.

Из проверенных атрибутов запись реально срабатывает только для
`_original.._active`.

| Атрибут | `rc` | Что произошло |
| --- | --- | --- |
| `_original.._active` | 0 | **значение записано** |
| `_original.._bad` | 0 | запрещён, значение прежнее, ошибки нет |
| `_original.._quality_code` | 0 | запрещён, значение прежнее |
| `_original.._exp_default` | 0 | запрещён, значение прежнее |
| `_corr.._value` | 0 | **не записалась** (см. ниже) |

### Расхождения с документацией

1. **`dpSetTimed(t, "DP.:_corr.._value", v)` не записывает значение.** Пример в
   документации нерабочий. У `_corr` ровно четыре атрибута (`_type`, `_value`,
   `_stime`, `_status64`), и `_value` там того же типа, что `_original.._value`,
   — дело не в типе значения. Запись подтверждена как невыполненная.
2. **Атрибута `_original.._per_active` на 3.18 нет.** Документация перечисляет
   его среди изменяемых пользователем; чтение даёт `rc = -1`, в составе 77
   атрибутов `_original` его не значится.
3. **Функции `makeUtcTime()` в CTL 3.18 нет.** Время задаётся `makeTime()`, и
   оно локальное.
   Текущее время берётся отдельно: `getCurrentTime()` отдаёт локальное
   время «сейчас» с точностью до наносекунд — в отличие от `makeTime()`,
   который только конструирует время из чисел.
4. **Предусловие «не раньше 1.1.1970» недостижимо средствами CTL.**
   `makeTime(1969, 12, 31, 23, 0, 0)` возвращает `1970.01.01 03:00:00` — CTL
   сам подставляет 1970 год. Проверить отказ по времени нечем, и в коде CTL
   такого отказа не возникает.
5. **Время `0` принимается**, и запись выполняется. Документация допускает
   `dpSetTimed(0, ...)` для конфигов тревог — это подтверждается, но работает
   шире, чем описано.

Несколько пар и форма `dyn_string` + `dyn_anytype` работают.

**Скрипт.** `examples/02-config/03_dpSetTimed.ctl` ✅ проверено, 22/22

**Типичные ошибки**

* Время раньше 1.1.1970 — отказ.
* Попытка писать в атрибут, который пользователю нельзя менять.
* `dpSetTimed(0, ...)` для не-`alert`-конфигов не поддерживается.

## dpSetTimedWait()

**Синопсис**

```c
int dpSetTimedWait(time t, string dp1, <type1> val1 [, string dp2, <type2> val2, ...]);
int dpSetTimedWait(time t, dyn_string dpnames, dyn_anytype values);
```

**Назначение.** `dpSetTimed()`, но **блокирующая** — ждёт ответ Event Manager.

**Ожидание.** **Blocking** (Waiting Control function).

Всё остальное идентично `dpSetTimed()`.

### Измерено на стенде — 21 проверка, ✅ проверено

**Асимметрия с `dpSetTimed()` — главный результат этого раздела.**

| Вызов | Запрещённый атрибут |
| --- | --- |
| `dpSetTimed()` | `rc = 0`, отказ **не виден** |
| `dpSetTimedWait()` | `rc = -1`, отказ **виден** |

Причина в том, что блокирующая версия дожидается ответа Event Manager, и в
ответе приходит сам отказ. Неблокирующая ответа не ждёт и отбрасывает его молча.

**Практический вывод: если нужен контроль ошибок записи — использовать
`dpSetTimedWait()`, а не `dpSetTimed()`.** Это единственное, что отличает их на
практике, а не время ожидания.

Остальное поведение, ограничения по атрибутам и все расхождения с документацией
те же, что у `dpSetTimed()` — см. раздел выше.

**Скрипт.** `examples/02-config/04_dpSetTimedWait.ctl` ✅ проверено, 21/21

## dpSetAlias()

**Синопсис**

```c
int dpSetAlias(string dp, string alias);
```

**Назначение.** Задаёт альтернативное имя (алиас) элемента точки данных.

**Параметры**

| Имя | Тип CTRL | Обяз. | Описание | Значение для примера |
| --- | --- | --- | --- | --- |
| `dp` | `string` | да | Элемент точки данных | `"Pump12.Command_On"` |
| `alias` | `string` | да | Алиас | `"P12Com_O"` |

**Возврат.** `0` — ок, `-1` — несуществующая/неверная точка данных.

**Ограничения**

* Алиас **только одноязычный** — одинаков для всех языков проекта.
* Алиас уникален в обе стороны: один алиас → один DPE, один DPE → один алиас.
* Алиас не может содержать символы, запрещённые в именах DP (см.
  [`nameCheck()`](01-create.md#nameCheck)).
* Алиасы можно искать через `dpNames("@alias")`.

```c
dpSetAlias("Pump12.Command_On", "P12Com_O");
```

**Ожидание.** **Blocking** (Waiting Control function).

**Скрипт.** `examples/02-config/01_metadata_functions.ctl`

**Типичные ошибки**

* Попытка задать два алиаса на один DPE — ошибка.
* Ошибка о уже существующем алиасе приходит только в `getLastError()`.

## dpGetAlias()

**Синопсис**

```c
string | dyn_string dpGetAlias(string | dyn_string dpName);
```

**Назначение.** Возвращает алиас указанного элемента.

**Параметры**

| Имя | Тип CTRL | Обяз. | Описание | Значение для примера |
| --- | --- | --- | --- | --- |

причина микробагов при сравнении).

```c
string alias = dpGetAlias("Pump12.Command_On");

DebugN(all);
```

**Скрипт.** `examples/02-config/01_metadata_functions.ctl`

**Типичные ошибки**

* Сравнение результата с `""` — при ошибке возвращается `" "`.
* Запрос алиаса у node-элемента (не DPE) не работает.

## dpSetFormat()

**Синопсис**

```c
int dpSetFormat(string dp, langString dpFormat);
```

**Назначение.** Задаёт формат отображения — строку формата `sprintf`.

**Параметры**

| Имя | Тип CTRL | Обяз. | Описание | Значение для примера |
| --- | --- | --- | --- | --- |
| `dp` | `string` | да | Элемент точки данных | `"mld_float."` |
| `dpFormat` | `langString` | да | Строка формата `sprintf` | `"%6.2f"` |

**Возврат.** `0` — ок, `-1` — ошибка.

> **Никаких проверок соответствия формата типу данных.** Если формат не подходит
> типу, `dpValToString()` вернёт не то значение, что хранится. Ответственность на
> пользователе.

```c
dpSetFormat("mld_float", "%6.2f");

langString format;

## dpSetDescription()

**Синопсис**

```

**Назначение.** Задаёт описание (комментарий) элемента. Заменяет `dpSetComment()`.

**Параметры**

| Имя | Тип CTRL | Обяз. | Описание | Значение для примера |
| --- | --- | --- | --- | --- |

```c
dpCreate("number_1", "ExampleDP_Int");
dpSetDescription("number_1", "Here is the comment");
DebugN(dpGetDescription("number_1."));
```

**Скрипт.** `examples/02-config/01_metadata_functions.ctl`

**Типичные ошибки**

* `@` в тексте описания неожиданно превращается в формат/единицу.
* Ожидание исторического доступа к комментариям — его нет.

## dpGetDescription()

**Синопсис**

```c
langString | dyn_langString dpGetDescription(string | dyn_string dp [, int mode]);
```

**Назначение.** Возвращает описание элемента; заменяет `dpGetComment()`.

**Параметры**

| Имя | Тип CTRL | Обяз. | Описание | Значение для примера |
| --- | --- | --- | --- | --- |
| `dp` | `string` / `dyn_string` | да | Элемент или точка данных | `"Valve17."` |
| `mode` | `int` | нет | Режим вычисления, см. ниже. По умолчанию `1` | `1` |

**Возврат.** `langString` / `dyn_langString` с описаниями на всех языках.

### Режимы `mode`

По умолчанию берётся из конфиг-элемента `dpGetDescriptionMode` в секции `general`
(значения `0`, `1`, `2`, `3`, `-1`, `-2`).

| Режим | Поведение |
| --- | --- |
| `-2` | Только описание DPE. Если нет — ошибка (внутренний режим) |
| `-1` | Описание DPE. Если нет — имя элемента, для корневого DPE — имя точки данных (внутренний режим) |
| `0` | Описание DPE. Если нет — имя DPE вида `DP.EL1.EL2` |
| `1` | **По умолчанию.** Описание DPE. Для корневой точки данных при отсутствии описания — `"RootNode Description DP"` + описание мастер-DPE. Для остальных — имя точки данных + описание мастер-DPE. Если и его нет — имя точки данных либо элемента |
| `2` | Описание DPE. Для корневой точки данных — описание мастер-DPE + `"RootNode Description DP"`. Для остальных — описание мастер-DPE + имя точки данных |
| `3` | Описание DPE. Для корневой точки данных — `"RootNode Description DP <ИмяЭлемента>"` + описание мастер-DPE. Для остальных — имя точки данных + имя элемента + описание мастер-DPE |

**Удаление описания.** Задание пустого описания физически удаляет его на DPE, но
`dpGetDescription()` всё равно вернёт **вычисленное** описание (по режиму).

### Измерено на стенде — 14 проверок, ✅ проверено

**Пустой результат не значит «нет описания».** Только `mode = -2` ничего не
подставляет и честно показывает наличие или отсутствие описания.

Для элемента **без** описания (`iVal`) подстановка выглядит так:

| `mode` | Результат |
| --- | --- |
| `-2` | `` — пусто, описания нет |
| `-1` | `iVal` — только имя элемента |
| `0`, `1`, `2`, `3` | `System1:dpdemo_cfgdesc_dp.iVal` — полное имя с системой |

**Описание корню точки данных задать нельзя.** `dpSetDescription(имяТочки)`
возвращает `rc = -1`, в журнале приходит
`SEVERE, ElementTable, findNameLocation, Problem with Typecontainer`. Причина
ровно та, о которой говорит документация: описание — свойство **элемента**, а
корень структуры элементом не является. Документация обходит это молча.

Прочее измеренное:

* описание элемента читается и пишется; имя элемента структуры — **без** завершающей точки, а корень одиночной точки — **с** точкой (см. замечание выше);
* задание пустого описания физически удаляет его, и `mode = -2` после этого
  возвращает пусто, а `mode = 1` — по-прежнему подставляет имя;
* несуществующий элемент и несуществующая точка → пустой результат;
* завершающая точка в имени элемента (`DP.fVal.`) ломает вызов — пусто.

**Скрипт.** `examples/02-config/10_dpGetDescription.ctl` ✅ проверено, 14/14

**Типичные ошибки**

* Пустой результат не значит «нет описания» — при `mode >= 0` подставляется имя.
* Описания у **DPE**, не у **DP**.

## dpCopyConfig()

**Синопсис**

```c
void dpCopyConfig(string dpSource, string dpDestination, dyn_string sConfig,
                  int &error, int iDriverNumber = -1);
```

**Назначение.** Копирует указанные конфиги с одного элемента на другой.

**Параметры**

| Имя | Тип CTRL | Обяз. | Описание | Значение для примера |
| --- | --- | --- | --- | --- |
| `dpSource` | `string` | да | Исходный элемент | `"ExampleDP_Arg1."` |
| `dpDestination` | `string` | да | Целевой элемент. **Тот же DPT, что и у источника** | `"ExampleDP_Arg2."` |
| `sConfig` | `dyn_string` | да | Список копируемых конфигов | `makeDynString("_address","_distrib")` |
| `error` | `int` | да, **ref** | Код ошибки. **Возврат — `void`** | `0` |
| `iDriverNumber` | `int` | нет | Номер драйвера. Не задан → используется номер источника | `-1` |

**Возврат.** `void`. Ошибка — только в `error` (коды как у [`dpCopy()`](07-copy.md#dpCopy)).

**Правила**

* Только для двух точек данных **одного типа**, элементы — **одного типа данных**.
* Конфиг `_original` копировать **нельзя**.
* Конфиг `_general` по умолчанию **не копируется**.
* Значения атрибутов по умолчанию **не копируются**.

**Смена номера драйвера.** При смене номера драйвера драйвер-специфичные конфиги
**теряются**. Для копирования на другой номер драйвера нужно явно перечислить все
конфиги драйвера:

```c
dpCopyConfig(src, dst, makeDynString("_distrib", "_address", "_smooth",
                                    "_cmd_conv", "_msg_conv"), error, iDriverNumber);
```

При копировании `_address` номер драйвера `iDriverNumber` указывать **обязательно**.

```c
dyn_string conf = makeDynString("_address","_distrib","_smooth","_msg_conv","_cmd_conv");
int error;
dpCopyConfig("ExampleDP_Arg1.", "ExampleDP_Arg2.", conf, error);
```

### Измерено на стенде — 18 проверок, ✅ проверено

Работает: `dpCopyConfig()` переносит конфиг на целевой элемент, и появление
конфига подтверждается чтением `_default.._type`.

Ошибка через `error` (ref) надёжно сообщается только о **несуществующих**
объектах: источник → `-1`, назначение → `-10`. Непустой `lastError()` не
возникает.

### Что функция НЕ проверяет

| Случай | Документация | Измерено |
| --- | --- | --- |
| `_original` | копировать нельзя | `error = 0`, проверки нет |
| элементы разных типов данных | нельзя | `error = 0`, проверки нет |
| конфига нет на источнике | — | `error = 0`, на целе конфига не появляется |

**Перенос конфига на другой элемент того же типа не работает:** `fVal` → `iVal`
даёт `error = 0`, но конфиг на `iVal` не появляется. Копирование привязано к
тому же элементу-приёмнику.

**Ловушка: пустой список конфиров роняет скрипт.** `dpCopyConfig()` с пустым
`sConfig` приводит к необробтанному исключению `Index out of range` в `mp.ctl`,
и скрипт обрывается, не печатая итог. Если список может оказаться пустым,
проверяйте `dynlen()` **до** вызова.

**Скрипт.** `examples/02-config/14_dpCopyConfig.ctl` ✅ проверено, 18/18

## dpCopyConfigMerge()

**Синопсис**

```c
void dpCopyConfigMerge(string sourceDpe, string destinationDpe,
                       dyn_string copyConfigs = makeDynString(),
                       int &error,
                       mapping forceAttributes = emptyMapping);
```

**Назначение.** Копирует конфиги с исключениями: отдельные атрибуты можно
принудительно не переносить.

**Параметры**

| Имя | Тип CTRL | Обяз. | Описание | Значение для примера |
| --- | --- | --- | --- | --- |
| `sourceDpe` | `string` | да | Исходный элемент | `"ExampleDP_Arg1."` |
| `destinationDpe` | `string` | да | Целевой элемент | `"ExampleDP_Arg2."` |
| `copyConfigs` | `dyn_string` | нет | Список конфигов. **Пустой массив = копировать все** | `makeDynString("_alert_class","_alert_hdl")` |
| `error` | `int` | да, **ref** | Код ошибки | `0` |
| `forceAttributes` | `mapping` | нет | Атрибуты, которые **не** копировать. Ключ — имя атрибута в схеме `<config>.<detail>.<attribute>`, значение — его значение. По умолчанию пусто → копируется всё | `_alert_hdl.._active` |

**Обязательный шаг перед вызовом:** `dpCopyConfigMergeBufferClear()`. Также буфер
надо чистить, если между двумя копированиями изменился исходный элемент, — иначе
скопируется **старая** информация.

Некопируемые конфиги (например `_offline`, `_original`) не копируются; в LogViewer
приходит сообщение об ошибке, конфиг пропускается.

```c
dyn_string copyConfigs = makeDynString("_alert_class", "_alert_hdl");
mapping forceAttributes;
int error;
dpCopyConfigMergeBufferClear();
dpCopyConfigMerge("ExampleDP_Arg1.", "ExampleDP_Arg2.",
                  copyConfigs, error, forceAttributes);
```

**Возврат.** `void`; ошибка — в `error`.

### Измерено на стенде — 22 проверки, ✅ проверено

* Явный список конфигов работает: конфиг создаётся на цели, значения переносятся.
* **Пустой список означает «скопировать все конфиги»** — подтверждено.
* **`forceAttributes` работает как надо** (название действительно вводит в
  заблуждение — это список атрибутов, которые **исключаются**). Ключ
  `_default.._value`: конфиг `_default` на цели создаётся, а его `_value`
  **не переносится**.
* Несуществующий источник → `error = -1`; несуществующее назначение → `error != 0`.
* В отличие от `dpCopyConfig()`, пустой список конфигов здесь не роняет скрипт.

**Главная ловушка раздела — устаревший кэш.** После первого слияния
изменения исходного элемента **не подхватываются**, даже если конфиг на цели
удалить и буфер очистить. Подробный разбор и обход — в
`dpCopyConfigMergeBufferClear()`.

**Скрипт.** `examples/02-config/15_dpCopyConfigMerge.ctl` ✅ проверено, 22/22

**Типичные ошибки**

* Забыть `dpCopyConfigMergeBufferClear()` → копируется устаревшее.
* Элементы разных типов данных.
* `forceAttributes` — именно то, что **не** копировать (название вводит в
  заблуждение).

## dpCopyConfigMergeBufferClear()

**Синопсис** `void dpCopyConfigMergeBufferClear();`

Очищает буфер `dpCopyConfigMerge()`. Если один и тот же исходный элемент
копируется несколько раз, информация читается **один** раз; буфер перезагружается
при копировании другого исходного элемента.

### Измерено на стенде — 11 проверок, ✅ проверено

**Обещание документации на 3.18 не выполняется.** Документация говорит: если
между двумя копированиями изменился исходный элемент, нужно очистить буфер,
иначе скопируется старая информация.

Проверенный эксперимент:

| Шаг | Действие | `_default.._value` на цели |
| --- | --- | --- |
| 1 | первое слияние, источник = 42.5 | **42.5** — верно |
| 2 | источник изменён на 7.75 | — |
| 3 | конфиг на цели удалён, буфер очищен | — |
| 4 | повторное слияние | **42.5** — старое значение |

Задержкой чтения это не объясняется: приём отслеживался циклом из шести чтений
с паузами. **Помогает единственное — сменить исходный элемент.** Те же значения,
взятые с другого элемента, копируются верно, причём буфер даже не приходится
чистить.

То есть `dpCopyConfigMergeBufferClear()` на 3.18 **не инвалидирует кэш по
исходному элементу**, и опереться на неё в рабочем коде нельзя. Документация
упоминает, что буфер перезагружается при копировании другого исходного
элемента, — это и есть единственно работающий механизм.

**Практический обход:**

* задавать и менять конфиги источника **до** первого слияния;
* либо брать конфиги с разных элементов;
* либо не полагаться на буфер и проверять результат чтением.

Функция объявлена `void`, ошибок не порождает.

**Скрипт.** `examples/02-config/16_dpCopyConfigMergeBufferClear.ctl` ✅ проверено, 11/11
