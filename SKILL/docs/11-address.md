# 11. Конфигурация `_address`: периферийный адрес (OPC UA, Modbus)

Этап вне общего жизненного цикла точки данных: не «создать точку данных», а
**привязать её элемент к конкретному адресу на PLC**.

**Область покрытия — только два драйвера: OPC UA и Modbus.** Остальные не
разбираются и не реализуются.

Источники: *Reference Tables → Datapoint configs → `_address`* и
*Reference Tables → `_address` (Peripheral address)*, документация 3.21.6;
плюс пример из опыта эксплуатации. Все константы проверены на CTL 3.18.

---

## 1. Правило номер один: конфиги пишем только через `dpSetTimedWait`

> ⛔ **Для манипуляции конфигурациями использовать исключительно
> `dpSetTimedWait(0, …)` или `dpSetTimed(0, …)`.**
>
> Первый аргумент — время источника — ставим `0`. Это не «просто так»: у
> конфигов есть история изменений, и запись с нулевым временем не раздувает её.
> Обычный `dpSet()` для этих задач не применяется.

Второй момент: **сначала создаётся конфиг, потом заполняются атрибуты.** Пока
не записан `_type`, писать в остальные атрибуты некуда — конфига не существует.

---

## 2. Порядок вызовов

```c
// Шаг 1. Точка данных должна существовать (иначе адрес писать некуда)
dpCreate("MyDevice", "ExampleDP_Int");

// Шаг 2. Номер драйвера. Если он не 1 — сначала _distrib (см. раздел 6)
int driverNumber = 1;
if (driverNumber != 1)
{
  dpSetTimedWait(0, dpe + ":_distrib.._type",   DPCONFIG_DISTRIBUTION_INFO,
                    dpe + ":_distrib.._driver", driverNumber);
}

// Шаг 3. Создать конфиг адреса и заполнить его одним вызовом
dpSetTimedWait(0, dpe + ":_address.._type",      DPCONFIG_PERIPH_ADDR_MAIN,
                  dpe + ":_address.._reference", address,
                  dpe + ":_address.._active",    TRUE,
                  dpe + ":_address.._drv_ident", "OPCUA");
```

Удаление адреса:

```c
dpSetTimedWait(0, dpe + ":_address.._type", DPCONFIG_NONE);
```

---

## 3. Константы `_type`

| Константа | Значение | Смысл |
| --- | --- | --- |
| `DPCONFIG_NONE` | `0` | нет периферийного адреса; удаление конфига |
| `DPCONFIG_PERIPH_ADDR_MAIN` | `16` | периферийный адрес |

> ⚠ **Ловушка, найденная на CTL 3.18.** В рабочих примерах часто встречается имя
> `DPCONFIG_PERIPH_ADDR`. **Такой константы в CTL 3.18 нет** — скрипт с ней не
> компилируется:
>
> ```
> CTRL, SEVERE, 73, Variable not defined, <файл>  Line: N, DPCONFIG_PERIPH_ADDR
> ```
>
> Правильное имя — `DPCONFIG_PERIPH_ADDR_MAIN`.

Проверенные на CTL 3.18 значения смежных констант:

| Константа | Значение |
| --- | --- |
| `DPCONFIG_NONE` | `0` |
| `DPCONFIG_DEFAULTVALUE` | `3` |
| `DPCONFIG_DISTRIBUTION_INFO` | `56` |
| `DPCONFIG_PERIPH_ADDR_MAIN` | `16` |

## 4. Атрибуты конфига `_address`

| Атрибут | Тип | Смысл |
| --- | --- | --- |
| `_type` | `type` | Тип периферийного соединения. `DPCONFIG_PERIPH_ADDR_MAIN` / `DPCONFIG_NONE` |
| `_reference` | `string` | **Строка адреса в периферии.** Формат зависит от драйвера — см. раздел 5 |
| `_active` | `bool` | Адрес активен. Неактивный адрес существует, атрибуты читаются и пишутся, но драйвер его **не использует**: нельзя ни передавать, ни принимать значения, соединение с PLC не строится, конфликты с другими адресами не проверяются |
| `_drv_ident` | `string` | Тип драйвера: `"OPCUA"`, `"MODBUS"` |
| `_datatype` | `int` | Тип значения в периферии; определяет преобразование между OA и PLC |
| `_direction` | `int` | Режим ввода/вывода. Биты 0–4 атрибута `_mode` |
| `_subindex` | `uint32` | Доступ к части адреса: отдельный бит в 32-битном слове и т. п. |
| `_offset` | `uint16` | Дополнительная информация об адресе, используемая драйвером |
| `_connection` | `string` | Используется некоторыми драйверами |
| `_internal` | `bool` | Внутренний бит. Смысл зависит от драйвера. Бит 5 `_mode` |
| `_lowlevel` | `bool` | Бит фильтра нижнего уровня. Бит 6 `_mode` |
| `_mode` | `char` | **Устарел.** Заменён на `_direction` + `_internal` + `_lowlevel` |
| `_interval` | `time` | **Устарел.** Заменён на `_poll_group` |
| `_start` | `time` | **Устарел.** Заменён на `_poll_group` |
| `_poll_group` | `dpid` | Ссылка на группу опроса. Задаётся именем системы + именем точки данных |

## 5. Строка адреса `_reference`

### 5.1 OPC UA

Формат:

```
Server$Subscription$Art$Variante$Item
```

| Поле | Что это | Пример из эталона |
| --- | --- | --- |
| `Server` | Имя точки данных `_OPCUAServer` **без** ведущего `_` | `kep` |
| `Subscription` | Имя точки данных `_OPCUASubscription` **без** `_` | `kep_sub` |
| `Art` | поле «артикул» | `1` |
| `Variante` | поле «вариант» | `1` |
| `Item` | **Node ID** элемента на OPC UA сервере | `ns=2;s=Simulation Examples.Functions.Ramp2` |

Собранная строка из эталона:

```
kep$kep_sub$1$1$ns=2;s=Simulation Examples.Functions.Ramp2
```

Сборка в коде:

```c
string address = serverName + "$" + subscriptionName + "$" + art + "$" +
                 variante + "$" + itemId;
```

> **Уточнение по пустым `Art` и `Variante`.** Встречается форма с пустыми полями
> (`сервер$подписка$$$nodeId` — два `$` подряд). Штатно настроенный в ParaMod
> адрес их **не оставляет пустыми**: там стоят `1$1`. Рабочей считается форма,
> которая получилась в эталоне; пустые поля отдельно не проверены.

#### 5.1.1 Разбор строки по полям

Схема из документации драйвера OPC UA (`OPC_UA/opc_ua_c_address.html`):

```
Server$Subscription$Kind$Variant$[numeric range]Item
```

| Поле | Название | Что это | Значение в проекте |
| --- | --- | --- | --- |
| 1 | `Server` | имя точки типа `_OPCUAServer` без подчёркивания | `kep` |
| 2 | `Subscription` | имя точки типа `_OPCUASubscription` без подчёркивания | `kep_sub` |
| 3 | **`Kind`** | данные, события или тревоги | **`1`** |
| 4 | **`Variant`** | `1` — NodeId, `2` — Browse Path | **`1`** |
| 5 | `Item` | сам NodeId или Browse Path | `ns=2;s=...` |

Пример из документации: `UASERVER1$Subscription1$1$1$ns=2;s=System.Pumpe1` — форма
совпадает с используемой у нас.

**Поле `Kind` вручную не настраивается.** Документация: *«The kind cannot be
configured in the peripheral address panel. This is derived from the
subscription type»*. Значит `1` — следствие того, что подписка `kep_sub`
типа Data. Для подписки событий или тревог поле будет другим, и задавать его
вручную бессмысленно.

**Поле `Variant` выбирает форму адресации.** В панели это переключатель
«ID узла» против «Просмотр пути» — то есть ровно то, что видно на снимке
Para. Значение `1` соответствует показанному «ID узла».

#### 5.1.2 Что проверено на стенде, а что нет

| Форма | Результат |
| --- | --- |
| `kep$kep_sub$1$1$<NodeId>` | ✅ **работает** |
| `kep$kep_sub$1$2$<BrowsePath>` | ⚠️ драйвер путь преобразует, но данные не пришли |
| `kep$$1$<NodeId>` — пустое поле подписки | ❌ драйвер отвергает: SEVERE `setAddress` |

Про Browse Path точнее. Драйвер вызывает `translateBrowsePathToNodeId` и
сообщает статус, то есть **Variant 2 поддерживается**:

| Путь | Статус |
| --- | --- |
| `/2:Simulation Examples.Functions.User3` | `BadNoMatch` |
| `/1:Simulation Examples.Functions.User3` | `BadNoMatch` |
| `/2:Simulation Examples/2:Functions/2:User3` | **`Good`** |
| `2:Simulation Examples.Functions.User3` | `BadNothingToDo` |

Путь, получивший `Good`, данных не привёл даже за 60 с, при этом повторный
запуск уже не вызывал `translateBrowsePathToNodeId` вовсе — путь
закешировался. **Итог: адресация через Browse Path на этом стенде не
доведена до рабочей, `Variant = 1` остаётся единственной проверенной формой.**

Про пустое поле подписки: документация допускает форму `Server$$Variant$Item`
для режима опроса, но драйвер 3.18 на такой адрес отвечает SEVERE и элемент
остаётся без данных. Практически: **подписку указывать надо**.

Примеры: `11_address_opcua_fields.ctl`, `12_address_opcua_browse.ctl`,
`13_address_opcua_browse2.ctl`.

### 5.2 Modbus

Формат адреса задаётся драйвером отдельно — см. документацию
*Defining the peripheral addresses of the Modbus/TCP driver*.

```
M.<ПЛК>.<FC>.<адрес регистра>
```

| Поле | Значение |
| --- | --- |
| `M` | драйвер Modbus |
| ПЛК | соответствует Slave ID устройства |
| FC | функциональный код: **1** — coils, **3** — read multiple registers |
| адрес | номер регистра или бита, с нуля |

Выбор FC следует из типа данных, а не из вкуса. Для логического элемента
нужен FC 1: попытка `M.1.3.4` с типом `boolean` заведомо нерабочая, и драйвер
об этом предупреждает: `Transformation/FC incompatibility for: M.1.3.4`.

Проверено на стенде: эмулятор Modbus TCP, шесть устройств Slave ID 1…6,
41 элемент, адреса вида `M.<SlaveID>.<FC>.<регистр>`.
Пример: `07_address_map.ctl`.

### 5.3 Для каждого Slave ID нужно описание PLC

Второе поле адреса — это номер PLC, а не Slave ID напрямую. Драйвер требует,
чтобы каждый использованный номер был описан во внутренней точке данных типа
`_Mod_Plc`. Без этого адрес молча не опрашивается:

```
PARAM,WARNING, 54, No host/unit address defined for PLC number: 6
```

Состав типа `_Mod_Plc` (прочитан `dpTypeGet`, 25 элементов): `PlcNumber`,
`UnitAddress`, `HostsAndPorts`, `TransactionTimeout`, `Coding`, `DrvNumber`,
`Active`, `Offset`, `ConfigFlags`, счётчики `SentFrames` / `RcvFrames` /
`RejFrames`.

**Описания PLC создаёт пользователь.** Скрипт только проверяет их наличие и
сообщает, какого не хватает.

Побочная сложность: типы `_Mod_Plc`, `_PollGroup`, `_OPCUAServer`,
`_OPCUASubscription` не отдают конфиги через `dpGetAllConfigs` — ноль.
Сведения лежат в структуре типа, читаются через `dpTypeGet`.

### 5.4 Запись: драйвер группирует запросы

Проверено на стенде, запись в coils и holding работает, но коды функций
отличаются от ожидаемых. Направление `DPATTR_ADDR_MODE_IO_POLL` (7) даёт и
чтение, и запись, и драйвер **не использует одиночные коды**:

| Что записано | Ожидалось | Фактически пришло |
| --- | --- | --- |
| один coil | FC 5 write single coil | **FC 15** write multiple coils |
| один регистр | FC 6 write single register | **FC 16** write multiple registers |

Журнал устройства:

```
[write] slave 6: FC15 coils 5..5 (1 байт)
[write] slave 6: FC16 holding 3..3 (Valve_Reg_Test)
```

**Направление 5 (`DPATTR_ADDR_MODE_OUTPUT_SINGLE`) не годится для записи.**
`dpSetTimedWait` возвращает `0`, значение читается обратно, но на устройство
ничего не уходит — в журнале запросов записи нет. Причина в семантике:
«выход, одиночное соединение по subindex», то есть значение живёт в OA.

Пример: `10_address_modbus_write.ctl`.

### 5.5 Свой сервер Modbus вместо GUI-эмулятора

`mtcpServerEmulator` не перечитывает конфигурацию без перезапуска: при
изменении файла приходится вручную останавливать приложение и заново выбирать
файл. Библиотеки `node-modbus` и `jsmodbus` помочь не могут — в npm это только
клиенты, серверной части нет.

Поэтому написан свой сервер без зависимостей: `tools/modbus-sim`,
см. [README](../tools/modbus-sim/README.md). Карта в `map.json`
подхватывается автоматически, проверено изменением диапазона на лету.

## 6. Конфиг `_distrib` и номер драйвера

Если менеджер драйвера запущен с номером, **отличным от 1** (например `-num 2`),
драйвер не сможет связать адрес с нужным менеджем, пока не настроен `_distrib`:

```c
int driverNumber = 2;    // ← спрашивается у пользователя
if (driverNumber != 1)
{
  dpSetTimedWait(0, dpe + ":_distrib.._type",   DPCONFIG_DISTRIBUTION_INFO,
                    dpe + ":_distrib.._driver", driverNumber);
}
```

| Константа | Значение |
| --- | --- |
| `DPCONFIG_DISTRIBUTION_INFO` | `56` |

> **Номер драйвера — всегда вопрос пользователю.** Угадывать его нельзя: он
> зависит от того, как запущен менеджер драйвера, и молча даст неверную привязку.

### 6.1 Привязка к соединению драйвера

Из документации: *«чтобы настроить периферийный адрес элемента точки данных,
откройте меню Configuration и выбери��е тип драйвера, используемый в проекте»*.

На практике (✓ измерено, `examples/11-address/02_address_opcua_read.ctl`) эта
ручная привязка **не потребовалась**: точка данных, созданная целиком скриптом
(`dpTypeCreate` → `dpCreate` → `_distrib` → `_address`), сразу начала получать
значения с PLC — 13 из 13 проверок пройдено.

Причина в том, что необходимые данные для привязки уже записаны скриптом:
строка `_reference` содержит имя сервера и подписки, а `_distrib.._driver` —
номер драйвера. Ручная привязка в PARA — это способ настроить то же самое через
GUI, а не обязательный дополнительный шаг.

Атрибут `_address.._connection` в эталоне содержит `"System1:"`. Он не
заполнялся вручную и в рассмотренном случае не понадобился.

> Оговорка документации остаётся в силе: *«если драйвер не запущен, поведение
> модуля PARA для конфига адреса не определено»*. Драйвер должен быть запущен.

## 6.1a. Что работает в строке адреса OPC UA, а что нет

Проверено на стенде, `11-address/11_address_opcua_fields.ctl` — **1 из 3**:

| Вариант | Строка адреса | Данные |
| --- | --- | --- |
| A | `kep$kep_sub$1$1$ns=2;s=…User3` | ✅ приходят |
| B | `kep$kep_sub$1$2$/2:Simulation Examples/2:Functions/2:User3` | ❌ молчит |
| C | `kep$$1$ns=2;s=…User3` | ❌ молчит |

Конфиг во всех трёх случаях записывается без ошибки — расходится именно приём
данных. Вариант B — Browse Path, он не заработал ни в одной из попыток.
Вариант C: **пустое поле подписки драйвер принимает в конфиге, но данных не
даёт**, поэтому «поле можно оставить пустым» — неверно.

Единственная рабочая форма — вариант A.

  всегда стоит сверять этой функцией, а не доверять описанию.

### 8.0. Какие `_direction` применимы к Modbus coil

это стоит проверить отдельно, а не считать готовым.

> Раньше здесь стояло обратное: «coil принимает только 0, 2, 3, 4, а 1, 5, 6, 7
> отвергаются с `rc = -1`», со ссылкой на перебор

## 8.1 Группа опроса `_poll_group` — обязательно для Modbus

> **Область действия.** Требование относится **только к драйверу Modbus**.
> Для OPC UA атрибут `_poll_group` не выставлялся ни разу, и всё работало:
> примеры `01`–`03` и `09` прошли с пустым значением `System1:`.
> Панель показывает группу опроса только при режиме приёма «опрос».

### Правило

Перед настройкой конфигурации `_address` пользователь **самостоятельно**
создаёт группу опроса. Скрипт узнаёт её имя одним из двух способов:

* пользователь сообщает имя точки данных группы опроса;
* либо скрипт берёт **первое попавшееся** имя точки данных типа `_PollGroup`.

**Скрипт никогда не создаёт группу опросы сам.**

Запись ссылки:

```
dpSetTimedWait(0, dpe + ":_address.._poll_group", pollGroup);
```

Значение — строка вида `System1:_1s`: имя системы **плюс** имя точки данных.

Поиск группы:

```
string findPollGroup()
{
  // dpNames возвращает имена уже с префиксом системы
  dyn_string all = dpNames("_**");
  for (int i = 1; i <= dynlen(all); i++)
  {
    if (dpTypeName(all[i] + ".") == "_PollGroup")
    {
      return all[i];
    }
  }
  return "";
}
```

### Почему без этого не работает

| Источник | `_poll_group` | Результат |
| --- | --- | --- |
| Настроено вручную, работает | `System1:_1s` | данные идут |
| Создано скриптом, атрибут не задан | пусто | адрес **не опрашивается**, молча |

Симптом especially коварен: `dpSetTimedWait` возвращает `rc = 0`, адрес в PARA
выглядит корректным, в логе ошибок нет — а данных нет. Проверено на стенде.

### Форма хранения

| Попытка чтения | Результат |
| --- | --- |
| `dpGet(item, int)` | `rc = 0`, но `WARNING: cannot assign variable of type DPIDENTIFIER_VAR` |
| `dpGet(item, string)` | `rc = 0`, значение `System1:_1s` |

Документация объявляет тип `dpid`; фактически внутри это `DPIDENTIFIER_VAR`.
В CTL атрибут работает как строка с полным именем точки данных.

Требование документации: *«The poll group is only set if it is correctly
specified by using the system name + datapoint name for the destination
system. Otherwise the poll group is not displayed in the para either.»* —
без префикса системы значение не выставится **и в PARA не отобразится**.

### Группа опроса — системная точка, и параметров в ней нет

| Проверка | Результат |
| --- | --- |
| `dpTypeName("_1s.")` | `_PollGroup` |
| конфиги | 11 стандартных, включая `_lock` и `_auth` |
| значения атрибутов | все пустые или нулевые |
| `_general..poll_time`, `_polltime`, `_interval`, `_mode`, `_active`, `_sync_time` | `rc = -1`, атрибута нет |

Параметры опроса — интервал, синхронизация, активность — **в точке данных не
хранятся**. Интервал, судя по имени `_1s`, задаётся вне неё: на стороне
драйвера либо через панель системного администрирования
(вкладка Drivers, кнопка Poll groups). Создать группу из CTL нечем — записывать
нечего. Отсюда и правило: группу создаёт пользователь.

### Удаление или переименование группы оставляет висячую ссылку

Проверено на стенде: группа `_1s` удалена, создана `_pool2s`. В конфигах всех
 ссылавшихся точек остался внутренний идентификатор удалённой точки:

```
dpdemo_mb_a.fVal  группа='(Type: 0 Sys: 1 Dp: 670 El: 0 : ..)'  rc=0
WARNING: could not convert DpIdentifier to string
```

`Dp: 670` — идентификатор удалённой `_1s`. `rc = 0`, то есть битая ссылка
**не диагностируется кодом возврата**: CTL просто не может превратить её в
имя. Исправление — перепривязать атрибет на действующую группу:

```
dpSetTimedWait(0, dpe + ":_address.._poll_group", findPollGroup());
```

**При этом опрос не прекращается.** Все семь точек продолжали получать данные
с висячей ссылкой. Значит:

| Состояние | Поведение |
| --- | --- |
| `_poll_group` пуст **изначально** | адрес не опрашивается, молча |
| `_poll_group` был задан, потом группа удалена | **опрос продолжается**, в конфиге остаётся битая ссылка |

Драйвер держит разрешённую конфигурацию сам. Поэтому после удаления группы
данные не «появятся» — они и не пропадали. Исправлять атрибут нужно для
целостности проекта, а не для восстановления опроса.

Практическое следствие: **удалять группу опроса, на которую кто-то ссылается,
нельзя**. Сначала снимать ссылки, потом удалять. Иначе в конфигах останутся
ссылки на несуществующие идентификаторы, которые не видны ни в PARA, ни по
коду возврата.

### 8.2 Сервер и Подписка OPC UA — берутся из системных точек

Отдельных атрибутов для них нет. Это первые два поля `_reference`:

```
<Сервер>$<Подписка>$<вариант>$<элемент>$<NodeId>
kep$kep_sub$1$1$ns=2;s=Simulation Examples.Functions.User3
```

Значения берутся из системных точек данных проекта:

| Точка данных | Тип | Что даёт |
| --- | --- | --- |
| `_kep` | `_OPCUAServer` | Сервер → `kep` |
| `_kep_sub` | `_OPCUASubscription` | Подписка → `kep_sub` |

В Para они отображаются **без подчёркивания**, в `_reference` подставляется
имя без подчёркивания. Имя выводится из полного имени точки строковыми
функциями CTL (см. раздел 8.3):

```
strpos("System1:_kep", "_")    -> 8
substr("System1:_kep", 9, 200) -> "kep"
```

Сверка полученного имени с реестром — без строковых функций, простой
конкатенацией:

```
dpExists("_" + server)                  -> TRUE
dpTypeName("_" + server + ".")          -> "_OPCUAServer"
```

Поля 3 и 4 (вариант и элемент) в проекте равны `1` и `1`. **Их источник не
установлен**, поэтому в скриптах они заданы константами с честной пометкой.

Пример: `09_address_opcua_from_system.ctl`.

### 8.3 Особенности CTL, найденные на стенде

#### Строковые функции

| Есть | Нет |
| --- | --- |
| `substr(s, from, len)` | `strstr` |
| `strpos(s, sub)` | `copy`, `left`, `right` |
| `strtok(s, sub)` — возвращает `int` | `strReplace`, `replace`, `mid`, `strFind` |

Индексы **с нуля**: `strpos("System1:_kep","_")` = 8,
`substr("System1:_kep",9,4)` = `"kep"`.

Проверено по одной функции в отдельном прогоне: неизвестное имя валит
компиляцию с `SEVERE, 72, Function not defined`, поэтому пакетная проверка
невозможна.

#### `dpExists` не работает для имён типов

Имя типа точки данных не является именем точки данных, поэтому `dpExists`
для него **всегда возвращает FALSE** — и проверка «тип удалён» на его основе
не значит ничего. Единственная правильная проверка — `dpTypeGet`:

```
dpTypeGet(dpt, probeNames, probeTypes)  != 0   // типа нет
```

#### `dpTypeDelete` асинхронен

После `dpTypeDelete` тип ещё какое-то время существует, и первый
`dpTypeCreate` получает `rc = -1` с `WARNING, 34, DM: DP already exists`.
Надёжный порядок:

1. удалить точку данных и дождаться `dpExists` = FALSE;
2. удалять тип в цикле, пока `dpTypeGet` возвращает 0;
3. создавать тип в цикле, пока `dpTypeCreate` возвращает 0.

Без этого в `07_address_map.ctl` все шесть типов рапортовали `rc = -1` и
работали только потому, что старый тип случайно совпадал с нужным.

#### `dpNames` отбирает по имени, а не по типу

Шаблон `dpNames("*_OPCUAServer")` вернул ноль, хотя точка `_kep` типа
`_OPCUAServer` существует. Отбор по типу делается перебором:

```
dyn_string all = dpNames("_**");
for (...) { if (dpTypeName(all[i] + ".") == wanted) { ... } }
```

#### Прочее

| Наблюдение | Следствие |
| --- | --- |
| CTL не поддерживает перегрузку функций | вспомогательные функции получают разные имена |
| `dyn_int x[];` и `dyn_int x[] = {...}` не компилируются | массивы заполняются циклом |
| Нет функций `len`, `charAt`, `strlen` в привычном виде | длины и символы считаются самостоятельно |
| Результат функции нельзя передать в параметр `&` | `dpTypeGet` требует отдельных переменных |
| `dpGet` принимает имя с префиксом системы | `dpNames` выдаёт `System1:...`, и это имя годно к употреблению |

#### Направление для OPC UA

`_direction` = `4` на панели OPC UA отображается как режим приёма
**«Спонтанный»**, а не «Опрос». То есть числовая константа из общей таблицы
раздела 8 не соответствует подписям панели драйвера. На работу не влияет:
данные приходят в обоих режимах. Наблюдение, а не установленный факт.

## 10. Замечания по проверенным случаям

### 10.1 Логический узел переключается — проверять нужно переход, а не срез

**Симптом, который сначала приняли за дефект.** Узел
`ns=2;s=Simulation Examples.Functions.User3` то отдаёт `true`, то `false`.
Проверка вида «прочитанное значение == true» ловит один мгновенный срез и
проваливается, хотя данные идут нормально.

**Как выглядит правильный узел.** На эталонной точке `f1.b_node` (тот же узел,
`datatype` 751, `_direction` 6) шесть замеров подряд с интервалом в секунду дали:

```
_online = FALSE, TRUE, TRUE, TRUE, FALSE, TRUE
```

Значение живое, узел переключается примерно раз в несколько секунд.

**Правильная проверка логического элемента** — зафиксировать **переход**:
если наблюдались и `true`, и `false`, данные идут. Одиночный срез не является
доказательством ни работы, ни неработы:

```c
bool sawTrue = false;
bool sawFalse = false;
for (int i = 1; i <= 25; i++)
{
  bool b;
  dpGet(dpe + ":_online.._value", b);
  if (b) { sawTrue = true; } else { sawFalse = true; }
  if (sawTrue && sawFalse) { break; }
  delay(1);
}
// данные идут тогда и только тогда, когда sawTrue && sawFalse
```

**Вывод по режиму направления.** Приём данных не зависит от `_direction`:
проверены и `DPATTR_ADDR_MODE_IO_SPONT` (6, как на эталоне), и
`DPATTR_ADDR_MODE_INPUT_POLL` (4) — логический узел приходит в обоих случаях.
Направление важно только в другом месте: два одинаковых **активных выхода** на
один адрес запрещены (см. грабли в разделе 9).

**Логических узлов на сервере ровно один.** Остальные boolean-узлы в `_Hints`
имеют `DataType = Null` и статус `Bad`, то есть значения не имеют. Если нужна
проверка записи — понадобится узел, доступный для записи.

### 10.2 Типа данных DPE `double` в WinCC OA нет

Константа `DPEL_DOUBLE` **не определена** — скрипт с ней не компилируется:
`SEVERE, 73, Variable not defined`. Проверены все `DPEL_*` из документации, кроме
этой константы они на месте (`DPEL_STRUCT`=1, `DPEL_BOOL`=23, `DPEL_INT`=21,
`DPEL_UINT`=20, `DPEL_FLOAT`=22, `DPEL_STRING`=25, `DPEL_BIT32`=24, `DPEL_BIT64`=50,
`DPEL_TIME`=26, `DPEL_CHAR`=19, `DPEL_DPID`=27, `DPEL_LONG`=54, `DPEL_ULONG`=58,
`DPEL_BLOB`=46, `DPEL_LANGSTRING`=42, `DPEL_TYPEREF`=41).

**Следствие:** узел типа `Double` принимается в элемент типа `float`. Драйвер
выполняет преобразование сам, точность двойной разрядности теряется. На стенде
`Ramp8` (`TypeIDDouble`, 150.75) корректно пришёл в элемент `float`.

## 11. Проверка результата

Два независимых слоя — они проверяют разное:

**Слой 1 — конфиг записан верно.** Читаем обратно все атрибуты, которые писали:

```c
string  reference;
bool    active;
string  drvIdent;
int     datatype;
int     direction;

dpGet(dpe + ":_address.._reference", reference);
dpGet(dpe + ":_address.._active",    active);
dpGet(dpe + ":_address.._drv_ident", drvIdent);
dpGet(dpe + ":_address.._datatype",  datatype);
dpGet(dpe + ":_address.._direction", direction);
```

Существование конфига `_address` проверяется его `_type`: он равен
`DPCONFIG_PERIPH_ADDR_MAIN` (16), то есть ненулевой. **Но полагаться на этот
признак нельзя вообще** — у конфига `_online` `_type` остаётся `0` даже при
заведомо настроенном конфиге. Общий надёжный признак — прочитать атрибут
данных конфига и проверить `rc` (см. [03-read.md](03-read.md#проверка-существования-конфига)).

**Слой 2 — значение реально приходит из PLC.** Это проверяет уже привязку и
драйвер, а не запись конфига:

```c
float value;
dpGetAsynch(makeTime(2026, 1, 1), dpe + ":_online.._value", value);
```

Для OPC UA дополнительно доступен `dpDirectRead()` — читает **напрямую из PLC**,
минуя Event Manager:

```c
float direct;
int rc = dpDirectRead(10000, dpe + ":_original.._value", direct);
```

`dpDirectRead()` работает **только с OPC UA**; для Modbus его нет.
Подробности — [04-write.md](04-write.md#dpdirectread).

## Полный рецепт привязки Modbus-адреса из скрипта

> Проверено на CTL 3.18, проект `<проект>`, драйвер Modbus 2, эмулятор TCP 504,
> устройство 1. Скрипты: `stp_final.ctl`, `stp_verify.ctl`.

### Обязательный набор — шесть атрибутов плюс `_distrib`

Без `_distrib` драйвер вообще не считает точку своей: молчит без ошибок.

```ctl
string dpe = "STP.Current_Temperature";

// 1. Распределение: БЕЗ ЭТОГО ДРАЙВЕР НЕ ОПРАШИВАЕТ ТОЧКУ
dpSetTimedWait(0, dpe + ":_distrib.._type",   DPCONFIG_DISTRIBUTION_INFO,
                  dpe + ":_distrib.._driver", 2);          // номер драйвера

// 2. Сам периферийный адрес
int rc = dpSetTimedWait(0,
                  dpe + ":_address.._type",      DPCONFIG_PERIPH_ADDR_MAIN,
                  dpe + ":_address.._reference", "M.1.4.0",   // M.<PLC>.<FC>.<регистр>
                  dpe + ":_address.._active",    TRUE,
                  dpe + ":_address.._drv_ident", "MODBUS",     // СТРОКА, не число
                  dpe + ":_address.._datatype",  561,          // INT16
                  dpe + ":_address.._direction", 4,            // опрос
                  dpe + ":_address.._poll_group", "System1:_1s");
```

### Что я делал неверно и почему адрес «не применился»

| Ошибка | Симптом |
| --- | --- |
| Не задан `_distrib` | Драйвер молчит: ни ошибок, ни запросов, `_bad = 1` |
| `_drv_ident` = число `2` вместо строки `"MODBUS"` | Адрес не опрашивается |
| `_datatype` не задан | Нет преобразования, для 32-битных — мусор |
| `_direction` не задан | Адрес не опрашивается |
| `_poll_group` не задан | Адрес не опрашивается, **это причина «тишины» №1** |
| Заданы лишние `_mode` и `_start` | В рабочем рецепте их нет; на результат не влияют |

Атрибутов `_address.._value` и `_address.._mode` в рабочей конфигурации **нет**.
Ссылка лежит в `_address.._reference`.

### Таблица `_datatype`

| Код | Тип | Применение в карте |
| --- | --- | --- |
| 561 | INT16 | `Temperature_Setpoint`, пороги тревог |
| 562 | INT32 | — |
| 563 | UINT16 | влажность, давление, PID, большинство holding |
| 564 | UINT32 | `Total_Operating_Hours`, `Serial_Number` |
| 566 | FLOAT | `Energy_Consumption`, `Firmware_Version` |
| 567 | BIT | дискретные входы и coils |

### Направление `_direction`

| Код | Смысл | Где применён |
| --- | --- | --- |
| 4 | опрос (только чтение) | все регистры и дискретные входы |
| 7 | вход/выход, можно писать | coils при FC 1 |

Направление 5 (`OUTPUT_SINGLE`) драйвер держит локально и на устройство **не отправляет**.

### Порядок слов: `CDAB`, а не `ABCD`

Полный рабочий цикл — от разбора референса пользователя до проверки данных —
описан в [12-map-to-ctl.md](12-map-to-ctl.md). Ключевое: скрипт точки не
пишется руками, а генерируется из карты, поэтому весь класс ошибок ввода
устранён механически.

Это отдельная находка, стоившая больше всего времени. Эталонная карта
`tools/modbus-sim/map.json` работала с `wordOrder = "CDAB"`. Новая карта была
создана с `"ABCD"` «по референсу пользователя», и все float-значения пришли
перевёрнутыми: `Firmware_Version` показывал −4.95e+32 вместо 3.14.

| Канал | `ABCD` | `CDAB` (верно) |
| --- | --- | --- |
| `Firmware_Version` | −4.95e+32 | **3.14** |
| `Energy_Consumption` | −2.36e−20 | **141.83** |
| `Total_Operating_Hours` | `bad = 1`, q = 86 | **40620** |
| `Serial_Number` | 2040745579 | **987654321** |

**Вывод: порядок слов задаётся в эмуляторе, а не в конфигурации точки OA.**
Скрипт на стороне OA ничего не знает о порядке слов — это преобразование
драйвера. Проверять надо всегда.

### Двухрегистровые значения в эмуляторе

`count = 2` и `signed = false` одинаково подходят под `float32` и под `uint32`.
Решает генератор в карте:

| Генератор | Трактовка |
| --- | --- |
| `sine` | всегда `float32` |
| `const` с дробным значением | `float32` |
| `ramp`, `const` с целым значением | `uint32` |

В `server.js` это решает функция `isFloatReg()`. При неверном выборе
`Total_Operating_Hours` приходил как `bad = 1` с заглушкой `2147483647`.

### Соответствие адресов карте — проверять обязательно

Первая версия точки объявляла `CurTemp` как `FLOAT` (566) на `M.1.4.0`, то есть
на два регистра `0..1`. В карте `ireg 0` — это `Current_Temperature` с
`count = 1`. Двойное чтение съело ещё и `Current_Pressure`, и оба канала
пришли битым мусором (`4.13e-39`).

**Правило: `count` в карте и `_datatype` в точке обязаны совпадать.** Перед
привязкой сверяй адреса с картой построчно, а не по памяти.

### Путь к элементу структуры — без завершающей точки

```ctl
dpGet("STP.CurTemp:_online.._value", v);    // элемент структуры — БЕЗ точки
dpGet("ExampleDP_Arg1.:_online.._value", v); // корень одиночной точки — С точкой
```

С точкой на элементе `dpGet` даёт `DP does not exist` и `rc = -1`.

### Имена элементов точки: `dpTypeGet`, а не `dpGetAllDPEs`

Функции `dpGetAllDPEs` не существует. Имена элементов берутся из типа точки:

```ctl
string tpn = dpTypeName("STP.");
dyn_dyn_string nm; dyn_dyn_int ty;
dpTypeGet(tpn, nm, ty);
for (int k = 2; k <= dynlen(nm); k++)        // строка 1 — сам тип
{ DebugN("STP." + nm[k][dynlen(nm[k])]); }
```

Существуют `dpGetAllAttributes`, `dpGetAllDetails`, но не `dpGetAllDPEs`,
`pn2` или `pt2`. Прежде чем выдумывать имя функции, ищи её в `scripts/libs/`
или в этом справочнике — «Function not defined» не означает, что функции нет.

```

Current_Pressure     = 45            (ожидаем 12..48)
Humidity             = 489           (ожидаем 350..620)
