## 1. Системные точки данных: правило «подчёркивание» ⛔

> **Точки данных и типы точек данных, имя которых начинается с `_`
> (например `_AESConfig`, `_ValueArchiv`, `_DataManager`, `_DpGroup…`,
> `_Stat_2_event_0_to_driver_2`) — СИСТЕМНЫЕ.**
>
> **В них нельзя ничего записывать и ничего изменять. Нельзя создавать,
> удалять, переименовывать и копировать «поверх» них. Нельзя писать в них
> через `dpSet()`, `dpSetWait()`, `dpDirectWrite()`, `alertSet*()`.**
>
> Это внутреннее состояние работающей системы OA. Запись в такие точки
> данных ломает работу системы и может привести к невосстановимому состоянию
> проекта.

Практические следствия для любого кода, который что-то перебирает или чистит:

| Что делаешь | Что обязательно |
| --- | --- |
| Перебираешь типы через `dpTypes()` | Отфильтровать имена, начинающиеся с `_` |
| Перебираешь точки данных через `dpNames()` | То же самое |
| Удаляешь «всё лишнее» | Проверять префикс `_` перед каждым `dpDelete()` |
| Создаёшь точку данных из «любого типа» | Не брать тип из выдачи без проверки |
| Пишете демо-скрипты | Имена собственных объектов **без** `_` |

Фильтр, который должен стоять в каждом переборе:

```c
// Возвращает true, если имя — системное. Такое нельзя трогать.
bool dpdIsSystem(string name)
{
  if (name == "") { return false; }
  string bare = name;
  // dpNames() возвращает имена с префиксом системы ("System1:_mp_ANALOG1"),
  // поэтому префикс системы нужно снять ДО проверки.
  if (substr(name, 0, 6) == "System")
  {
    int colon = strpos(name, ":");
    if (colon > 0) { bare = substr(name, colon + 1); }
  }
  if (bare == "") { return false; }
  return substr(bare, 0, 1) == "_";
}
```

> **Почему префикс системы надо снимать.** ✓ измерено: `dpNames()` возвращает имена
> вида `System1:_mp_ANALOG1`. Наивная проверка `substr(name, 0, 1) == "_"` на таком
> имени даст `false`, и системная точка данных пройдёт как пользовательская.

Масштаб проблемы на стенде: **227 системных типов против 35 пользовательских** из
262. То есть ~87 % типов в проекте — неприкосновенны.

Все примеры в `examples/` следуют этому правилу: собственный префикс — `dpdemo`
(без подчёркивания), а функция выбора типа всегда отбрасывает системные имена.

## 2. Что такое точка данных

| Объект | Смысл |
| --- | --- |
| **DP** (datapoint) | Именованная точка данных верхнего уровня. Имеет имя и **числовой ID** |
| **DPE** (datapoint element) | Элемент точки данных. Только у DPE есть тип данных, значение и конфиги |
| **DPT** (datapoint type) | Шаблон структуры. Описывает, какие DPE будут у DP. **DPT должен существовать до `dpCreate()`** |
| **Config** | Набор атрибутов, вариант хранения одного и того же значения |
| **Detail** | Подраздел внутри конфига (например `_alert_hdl`) |
| **Attribute** | Отдельный атрибут конфига (например `_value`) |

Связь: `DPT` → задаёт структуру → `DP` создаётся по `DPT` → внутри `DP` живут `DPE`.

### 2.1 Идентификатор точки данных (DP identifier)

Полный идентификатор имеет вид:

```
[System:]DP.DPE.config.detail.attribute
```

| Пример | Что означает |
| --- | --- |
| `Valve17` | сама точка данных |
| `Valve17.opening` | элемент `opening` |
| `number_1.` | «точка уровня 1» — корень структуры. **Точка в конце обязательна** |
| `Valve17.opening:_original.._value` | атрибут `_value` конфига `_original` |
| `Valve17.opening:_default.._type` | атрибут `_type` конфига `_default` |
| `Engine.setpoint.engineSpeed` | три уровня структуры |
| `System1:ExampleDP_Arg1` | явно указанная система в распределённой установке |
| `_original.._value` | безымянный идентификатор — тоже допустим вход для `dpExists()` |

> **Префикс системы можно опускать.** `System1:ExampleDP_Arg2.` и
> `ExampleDP_Arg2.` — эквивалентны. Префикс нужен только в распределённой
> установке, когда надо обратиться к чужой системе. Поэтому в примерах и в
> рабочем коде префикс `System1:` обычно не пишут, и вопрос «какой у меня номер
> системы» снимается: он вообще не нужен.
>
> ⚠ Осторожно: `dpNames()` **выдаёт** имена с префиксом (`System1:_mp_ANALOG1`),
> даже если вы запрашивали без него. Это влияет на сравнение строк и на фильтр
> системных имён — см. раздел 1.

Две тонкости, на которых чаще всего спотыкаются:

1. **Точка после имени DP** — не опечатка. `dpGetDescription("Valve17.")` и
   `dpGetDescription("Valve17")` — разные запросы. Точка фиксирует, что запрошен
   элемент первого уровня, а не сама точка.
2. **Двойная точка в `config..attribute`** — между конфигом и атрибутом пустой detail,
   поэтому разделителей два.

Части идентификатора проверяются функцией [`dpExists()`](01-create.md#dpExists) —
она возвращает `true`, если **хотя бы одна** часть разрешается. Поэтому
`dpExists(":")` возвращает `true` всегда и бесполезен. Чтобы проверить конкретный
уровень, добавляют `dpSubStr()`:

```c
bool e = dpExists(dpSubStr(ident, DPSUB_DP));   // существование именно DP
```

### 2.2 Что можно передать в `dpExists()`

`sys`, `DPT`, `DP`, `DPE`, `config`, `detail`, `attr` — любой из этих уровней.

Отдельного типа CTRL для «идентификатора точки данных» нет. Но такой идентификатор
можно получить как `anytype` из ответа `dpQuery*()` и передать его прямо в
`dpExists()` — см. пример в [01-create.md](01-create.md#dpExists).

## 3. Конфиги: где лежит значение

Один и тот же физический смысл (текущее значение, время, качество) хранится в
разных **конфигах**. Основные:

| Config | Смысл |
| --- | --- |
| `_original` | значение, записываемое пользователем/скриптом. «Оригинал» процесса |
| `_corr` | скорректированное значение (ручная правка истории, `dpSetTimed`) |
| `_online` | значение, полученное драйвером, актуальное |
| `_offline` | последнее значение, полученное драйвером (в том числе при потере связи) |
| `_lock` | блокировка редактирования |
| `_general` | общие настройки DPE |
| `_default` | значение по умолчанию |
| `_alert_hdl`, `_alert_class` | обработка и классификация тревог |
| `_address`, `_distrib`, `_smooth`, `_msg_conv`, `_cmd_conv` | конфиги драйвера |
| `_ValueArchiv` | архивные значения |

**Конфигов может быть много, и они создаются явно.** Конфиг не создаётся сам
просто оттого, что вызвали `dpSet()`. Чтобы конфиг появился, надо записать в его
атрибут `_type` соответствующую константу:

```c
dpSet("Valve17.opening:_default.._type", DPCONFIG_DEFAULTVALUE);  // создать _default
dpSet("Valve17.opening:_default.._type", DPCONFIG_NONE);          // удалить _default
```

### 3.1 Конфиг и атрибут по умолчанию

Если в идентификаторе конфиг или атрибут опущены, функция подставляет эти значения
**и добавляет их внутренне**:

| Функция | Подставляется по умолчанию |
| --- | --- |
| `dpSet*()` | `_original.._value` |
| `dpGet()` | `_online.._value` |
| `dpGetAsynch()` | `_offline.._value` |
| `dpGetPeriod()` | `_offline.._value` |
| `dpConnect()` | `_online.._value` |
| `dpDisconnect()` | `_online.._value` |

> **Ловушка.** `dpSet("dp.")`, `dpGet("dp.")`, `dpConnect("dp.")` работают с
> **разными** конфигами. Для скрипта «записал — прочитал» это может выглядеть как
> потеря данных. Всегда пишите конфиг и атрибут явно: `dp._original.._value`.

Узнать полный список атрибутов и detail-ов любого конфига можно программно:

```c
DebugN(dpGetAllAttributes("_original"));  // все атрибуты конфига
DebugN(dpGetAllDetails("_lock"));         // все detail-ы конфига
DebugN(dpGetAllConfigs("ExampleDP_Arg1.:"));  // конфиги, допустимые для DPE
DebugN(dpGetAllConfigs(23));              // конфиги, допустимые для типа данных (23 = bool)
```

## 4. Типы данных DPE (константы `DPEL_*`)

Нужны для `dpTypeCreate()`. Значения — целые числа, в `dyn_dyn_int` структура DPT
строится именно ими:

| Константа | Тип |
| --- | --- |
| `DPEL_BOOL` | bool |
| `DPEL_BIT8` … `DPEL_BIT32` | битовые поля |
| `DPEL_INT8/16/32` | целые |
| `DPEL_UINT8/16/32` | беззнаковые целые |
| `DPEL_FLOAT` / `DPEL_DOUBLE` | с плавающей точкой |
| `DPEL_STRING` | string |
| `DPEL_STRUCT` | структура (вложенный уровень) |
| `DPEL_TYPEREF` | **ссылка на тип** = **41** |

`DPEL_TYPEREF` вставляется числом `41`, а имя типа-ссылки кладётся **в текстовую
структуру** на ту же позицию. Это неочевидно, поэтому разбор — в
[01-create.md](01-create.md#dpTypeCreate).

## 6. Шаблоны поиска (`dpNames`, `dpQuery`)

Подстановки работают внутри одного уровня:

| Шаблон | Что ищет |
| --- | --- |
| `*` | любой уровень целиком |
| `*.*` | ровно два уровня |
| `Engine.setpoint.engineSpeed` | точное имя |
| `*DP*` | подстрока внутри уровня |
| `Engine.*.*` | все элементы на 3-м уровне дерева Engine |
| `{*.Ala.*,*.Ala*}` | список вариантов (фигурные скобки) |
| `:*` | все **конфиги** |
| `:config.*` | все **detail-ы** |
| `:config.detail.*` | все **атрибуты** |
| `System2:@somealias` | по **алиасу** (`@` в начале) |

Важно: для `dpType` в `dpNames()` подстановки **не работают** — только точное имя.
Для распределённых систем систему указывают в шаблоне: `dpNames("System1:Valve17.**")`.

## 7. Blocking-функции и где их нельзя вызывать

Две независимые вещи, которые часто путают.

**1. Waiting Control functions.** Функции, которые не возвращают управление, пока
Event Manager не ответит. Из нашей категории их много:

`dpCreate()`, `dpSetWait()`, `dpSetTimedWait()`, `alertSetWait()`,
`alertSetTimedWait()`, `dpTypeCreate()`, `dpSetAlias()`, `dpSetComment()`,
`dpSetDescription()`, `dpSetFormat()`, `dpNames()`, `dpQueryConnect*()`,
`dpWaitForValue()`, `dpGetPeriod()`.

Практические следствия:

* в единицах примера они стоят дороже неблокирующих аналогов;
* если Event Manager не запущен, скрипт **зависает**, а не падает;
* в распределённой установке `dpSetWait()` ждёт ответа Event Manager **другой**
  системы (через dist manager).

**2. Запрет контекста.** Функции категории Datapoint Functions **нельзя вызывать
в контексте event manager** — то есть не из кода, который сам исполняется внутри
Event Manager. Для обычных `.ctl`-скриптов, запускаемых через `WCCOActrl.exe`,
ограничение не действует.

### 7.1 Один вызов `dpSet()` — одна система

`dpSet()` и `dpSetWait()` **нельзя** использовать для точек данных разных систем
в одном вызове:

```
WCCOAui (1), ..., PARAM,SEVERE, 175, this request cannot address more than one system, ...
WCCOAui (1), ..., CTRL, WARNING, 76, Invalid argument in function,
```

Нужны отдельные вызовы на каждую систему.

## 8. Ограничения, о которых надо знать заранее

| Ограничение | Смысл |
| --- | --- |
| `maxConnectMessageSize` | `dpConnect*` могут не доставить всё, что подписано. Значение по умолчанию может быть мало — при необходимости увеличить в конфиге проекта |
| `maxDpNamesCount` | Ограничивает число точек, возвращаемых `dpNames()`. При превышении — сообщение об ошибке |
| `atomicDpSet` | В секции `general` конфига. `atomicDpSet = 1` делает операции записи в `_original`, `_lock`, `_general` атомарными: либо всё, либо ничего. По умолчанию выключено |
| Структуры | Запрос DPE типа `struct` шлёт в LogViewer предупреждение `getDpValueAttribut: no config`. **Последним элементом DP рекомендуется делать простой тип** (`bool`, `int`, `float`), а не структуру |
| Диапазоны значений | При выходе за диапазон `dpSet()` **не** генерирует исключение и **не** пишет ошибку |
| Повтор атрибута | В одном `dpSet()` нельзя присвоить одному атрибуту два значения: принимается первое, остальные отбрасываются, возврат `0`, ошибка в `getLastError()` |
| Рост времени обработки | С увеличением числа пар «атрибут — значение» время обработки растёт нелинейно |

## 9. Обработка ошибок: единый механизм

Почти все функции возвращают `0` / `-1` / `false`, а **причину** отдают через
`getLastError()`.

```c
int rc = dpSet("dp.:_original.._value", 1);
if (rc != 0 || dynlen(getLastError()) > 0) {
   DebugN("dpSet failed:", rc, getLastError());
}
```

Два исключения, которые ломают это правило:

* **`dpCreate()` может вернуть `0` (успех), когда точка данных фактически не создана** — например, из-за clash имён. Проверять только `getLastError()` мало, нужно подтверждать `dpExists()`.
* `dpCopyConfig()`, `dpCopyConfigMerge()` возвращают `void` — код ошибки приходит через параметр `int &error`.

```
Ожидание      — блокирует ли (→ выбор режима запуска)
Скрипт        — путь к .ctl в examples/
Типичные      — грабли
```

Секции «Значение для примера», «Предусловия», «Побочные эффекты» — это ровно те
данные, которые нужны механически, чтобы собрать из документации скрипт.
