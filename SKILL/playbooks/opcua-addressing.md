# OPC UA: адреса и обход сервера

> Статус: **проверено сквозным образом.** Сервер Kepware KEPServerEX V6,
> драйвер OPC UA номер 3, пример `11-address/22_address_opcua_live.ctl`,
> 6/6 PASS. Значение приходит (`quality = 128`, `_stime` обновляется) и
> меняется. Независимая сверка с сервером через `opcuactl monitor value`
> по временны́м меткам сошлась: темп одинаковый, расхождение растёт
> линейно, то есть это задержка опроса, а не разница данных.
>
> Не сделано: генератора адресов OPC UA и проверки записи.

## Что нужно от пользователя

Готовить вручную приходится только три вещи, и из CTL это не сделать:

1. **драйвер OPC UA** запущен в проекте; номер берётся из командной строки
   процесса `WCCOAopcua.exe -num N -PROJ <проект>`;
2. **точка типа `_OPCUAServer`** с настроенным endpoint, например
   `opc.tcp://хост:порт`;
3. **точка типа `_OPCUASubscription`**, в monitored items которой есть нужные
   Node ID.

Дальше всё делается из скрипта: сервер и подписка находятся по типу, адрес
собирается, значение читается.

## Формат адреса, проверенный на стенде

```
<сервер без _>$<подписка без _>$<variant>$<element>$<NodeId сервера>
```

Точка `_opc_ua_con`, точка `_subs`, variant 1, element 1 и узел сервера
`ns=2;s=Channel1.Device1.Tag1` дают

```
opc_ua_con$subs$1$1$ns=2;s=Channel1.Device1.Tag1
```

Ведущее подчёркивание в адрес **не входит**: точка `_opc_ua_con` даёт в
адресе `opc_ua_con`. В панели имена тоже показываются без него.

Сервер и подписка ищутся по типу, а не по имени:

```ctl
string findByType(string want)
{
  dyn_string all = dpNames("**");
  for (int i = 1; i <= dynlen(all); i++)
  {
    if (dpTypeName(all[i] + ".") != want) { continue; }
    int pos = strpos(all[i], "_");
    return substr(all[i], pos + 1, 200);
  }
  return "";
}
```

`dpNames()` отбирает по **имени**, а не по типу, поэтому шаблон
`*_OPCUAServer` не годится и даёт ноль. Перебирать надо всё и проверять
`dpTypeName`.

Обязательный набор атрибутов `_address` тот же, что для Modbus, но
`_drv_ident` строкой `"OPCUA"`, а `_datatype` и `_direction` пишутся явно:
для OPC UA значение `0` не значит ничего, `DEFAULT` здесь 750, а не 0.

## Состав подписки не перечислить

`dpGetAllAttributes` и `dpGetAllConfigs` на точках типа `_OPCUAServer` и
`_OPCUASubscription` возвращают **ноль элементов**. Это системные точки с
конфигами, и из CTL их содержимое не обойти. Проверка с системным
префиксом `System1:` тоже не помогает.

Практический вывод: убедиться, что узел есть в подписке, можно только
попыткой чтения. Если значение не пришло, это может быть любой из трёх
причин — нет сервера, нет подписки, нет узла в подписке, — и различить их
из CTL нельзя. Спрашивай пользователя или смотри журнал драйвера.

## Генератор: карта CSV в готовый CTL

Инструмент `tools/gen-opcua-dp.js`. Карта берётся из CSV Kepware, типы и
факт наличия узла — с самого сервера.

```powershell
node .\tools\gen-opcua-dp.js .\tools\opcua\Functions.csv ``
     --out .\examples\11-address\23_address_opcua_from_map.ctl ``
     --endpoint opc.tcp://<хост>:<порт> ``
     --path "Simulation Examples.Functions" ``
     --dp FUNCS --dpt funcs_t --drv 3 --allow-missing
```

| Ключ | Смысл |
| --- | --- |
| `--endpoint` | сервер; без него сверка с сервером отключается |
| `--path` | папка на сервере, из неё строится `ns=2;s=<path>.<TagName>` |
| `--dp`, `--dpt` | имена точки и типа |
| `--drv` | номер драйвера, по умолчанию 3 |
| `--no-resolve` | не обращаться к серверу, взять типы из карты |
| `--no-verify` | не добавлять блок проверки данных |
| `--allow-missing` | не считать ошибкой теги, которых нет на сервере |
| `--keep` | не удалять существующую точку |

### Что даёт сверка с сервером

Сервер — источник истины, а не запись в карте. На карте `Functions.csv`
24 тега, и сверка нашла **6 тегов, которых сервер не отдаёт**:

```
Ramp5    LLong   нет узла
Ramp6    QWord   нет узла
Ramp7    LLong   нет узла
Random6  LLong   нет узла
Random7  QWord   нет узла
Random8  QWord   нет узла
```

То есть **Kepware не отдаёт `LLong` и `QWord` по OPC UA**. Без сверки эти
шесть точек создались бы молча и не дали бы данных. Остальные 18 типов
совпали с картой один в один: `Long`→`Int32`, `Word`→`UInt16`,
`Short`→`Int16`, `Float`→`Float`, `Double`→`Double`.

Генератор печатает и расхождения типов, когда тип в карте и на сервере
различаются, и умеет считать узлы осмысленными, отбрасывая `_System`,
`_Statistics`, `_Hints`, `_Features`, `_Alarms` и скалярные метаданные
тега `_Address`, `_Description`, `_Scaling*`.

### Запись: доказана

Пример `examples/11-address/24_address_opcua_write.ctl`. Локально `dpSet`
проходит для всех типов, и на сервере совпало 7 из 7:

| Тип | Код | Элемент | Записано | На сервере |
| --- | --- | --- | --- | --- |
| Int32 | 756 | `DPEL_INT` | −12345 | −12345 |
| UInt16 | 755 | `DPEL_UINT` | 60000 | 60000 |
| Int16 | 754 | `DPEL_INT` | −300 | −300 |
| **Int64** | **758** | **`DPEL_LONG`** | 123456789 | 123456789 |
| **UInt64** | **759** | **`DPEL_ULONG`** | 2000000000 | 2000000000 |
| Boolean | 751 | `DPEL_BOOL` | TRUE | True |
| Float | 760 | `DPEL_FLOAT` | 2,25 | 2,25 |
| UInt32 | 757 | `DPEL_UINT` | 2000000000 | 2000000000 |
| String | 762 | `DPEL_STRING` | `ZAPIS` | `ZAPIS` |

То есть 64-битные типы **тоже проверены**, вопреки более раннему выводу.

### Границы, которые нашла проверка записи

**Литералы целых в CTL 32-битные знаковые.** `dpSet("...", 4000000000)`
даёт `Syntax error, overflow in implicit constant conversion`, даже если
точка беззнаковая. Потолок 2147483647.

**Одному узлу нельзя соотнести две точки.** Повторная привязка уже занятого
узла даёт `rc = -1` и пустой `_reference` **без сообщения об ошибке**.
Элемент при этом существует, `dpSet` по нему работает, значение меняется
локально — но на сервер не уходит. Без сверки с сервером это выглядит как
успешная запись. В моём прогоне ровно так проявились `DWord1` и `String1`.

**Пиши только в узлы, которыми не управляет устройство.** В устройстве
`16 Bit Device` регистры `R` растут сами: `Long1` на 31 за 3 секунды,
`Word1` на 29, `Float1` на 36,25. Запись ложится, но устройство тут же
продолжает менять значение, и сверка покажет расхождение в несколько сотен.
Доказать запись можно на статичных узлах: регистры `K` и `S` в том же
устройстве стоят и держат записанное.

## Ответ про подписку

**Узел в подписку добавлять не пришлось.** Подписка `_subs` создавалась
для `Channel1.Device1.Tag1` и `Tag2`, а 18 тегов из `Functions` в ней не
были, и всё равно пришли значения: 18 из 18 `quality = 128`.

Оговорка честности: перечислить состав подписки из CTL нельзя,
`dpGetAllAttributes` и `dpGetAllConfigs` на системных точках дают ноль.
Поэтому утверждать, что подписка не нужна вообще, нельзя — можно лишь
сказать, что для этих 18 узлов добавлять их в подписку до запуска
не потребовалось.

### Ловушка с кодировкой, противоположная PowerShell

| Тип файла | BOM | Почему |
| --- | --- | --- |
| `.ps1` | **нужен** | PowerShell 5.1 без BOM читает как Windows-1251, кириллица ломает разбор |
| `.ctl` | **не нужен** | `WCCOActrl` спотыкается о BOM на первой строке: `Syntax error, Line: 1` |

`Set-Content -Encoding UTF8` в PowerShell 5.1 ставит BOM. Для `.ctl` это
гарантированная ошибка на первой строке. Пиши через
`[System.IO.File]::WriteAllText($p, $s, [System.Text.UTF8Encoding]::new($false))`.

## Обход сервера через opcuactl

Инструмент лежит в `tools/opcuactl/`, лицензия MIT, версия 0.2.0.

```powershell
$o = '.\tools\opcuactl\opcuactl.exe'
$e = 'opc.tcp://<хост>:<порт>'

& $o ping    -e $e
& $o discover endpoints -e $e
& $o browse  children  -e $e --node 'i=85'
& $o get     value     -e $e --node 'ns=2;s=Channel1.Device1.Tag1'
& $o get     attr      -e $e -n 'ns=2;s=Channel1.Device1.Tag1' --all
& $o get     vars      -e $e --node 'i=85' --recursive -f json
& $o monitor value      -e $e --node 'ns=2;s=Channel1.Device1.Tag1' -f json
```

### Что работает и что молчит

| Команда | Результат |
| --- | --- |
| `ping` | связь есть, 2,1 мс |
| `discover endpoints` | 5 endpoint'ов Kepware, анонимный токен разрешён |
| `browse children` | дерево пространства имён |
| `get value` | значение, тип и статус |
| `get attr --all` | 22 атрибута узла, `DataType`, `AccessLevel` |
| `get vars --recursive -f json` | вся карта сервера: 4085 переменных, 962 КБ. **Но `AccessLevel` не отдаёт** |
|`export nodes --include-attrs -f json` | **метаданные с доступом**: `nodeId`, `nodeClass`, `dataType`, `accessLevel`. Правильный источник для генератора |
| `monitor value -f json` | поток изменений с метками времени |
| `get vars` без `--recursive` | пусто, только заголовок |
| `get attr` без `--attr` и без `--all` | пусто |
| `monitor items` | такой подкоманды нет, есть `monitor value` |

Ключ `--recursive` обязателен, без него `get vars` молчит.

### Как на самом деле получить доступ к узлу

`get vars` бесполезен для этого: он отдаёт `nodeId, browseName, displayName,
typeDefinition, dataType, value, status` и **не содержит** `accessLevel`.
Нужен `export nodes --include-attrs`:

```powershell
& $o export nodes -e $e -n "ns=2;s=Data Type Examples.16 Bit Device" ``
         --depth 3 --include-attrs -f json
```

Он отдаёт плоский массив, где у переменных есть `dataType` и `accessLevel`.
Значение приходит **строкой** вида `AccessLevelType(3)`, число надо вытаскивать
регуляркой: 1 — чтение, 2 — запись, 3 — чтение и запись. У папок
`AccessLevelTypeNone`, поэтому фильтруй по `nodeClass == NodeClassVariable`.

Генератор `tools/gen-opcua-dp.js` использует именно эту команду, а не
`get vars`. Плюс она не читает значения, и обход заметно быстрее.

| 16:17:05 | 2286 | 2288 | +2 |
| 16:17:08 | 2308 | 2311 | +3 |
| 16:17:11 | 2333 | 2339 | +6 |

### На чём споткнуться

- **Идентификаторы.** В колонке `BROWSE NAME` вывод показывает `2:Tag1` —
  это отображение, а не идентификатор. Для конфига нужен столбец
  `NODE ID`, то есть `ns=2;s=Channel1.Device1.Tag1`.
- **Диагностика неотделима от данных.** В карте 1865 строковых и 949
  вещественных переменных, и почти все служебные. Фильтровать по
  `_System`, `_Statistics`, `_Hints`, `_Features`, `_Alarms`.
- **Защищённый канал.** Без `--insecure-skip-verify` и клиентского
  сертификата соединение может не подняться. Не выключай проверку молча:
  предупреждай пользователя.
- **Имя типа.** В выводе `get value` тип приходит как `TypeIDUint16`, в
  `get node` как `UInt16`. Разбор JSON должен понимать оба.

## Чего нет

- Генератора адресов OPC UA из карты. Генератор Modbus жёстко завязан на
  формат `M.<PLC>.<FC>.<регистр>` и на коды 561…567, для OPC UA не подходит.
- Проверки записи в OPC UA. Для Modbus запись подтверждается запросом на
  устройстве, здесь такого подтверждения пока нет.
- Эмулятора OPC UA. Рабочего стенда без реального сервера не будет.

## Первый прогон на новом стенде

1. Убедиться, что драйвер OPC UA запущен, и взять его номер из процесса.
2. `opcuactl ping` — связь.
3. `opcuactl discover endpoints` — какие endpoint'ы отдаёт сервер.
