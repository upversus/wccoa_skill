# Приёмка на чужом материале

Проверка, которой не хватало. Все предыдущие прогоны делались на картах,
которые я либо строил сам по референсу в той же сессии, либо получал вместе
с описанием. Здесь иначе.

## Как построена проверка

Три условия, которые отличают её от предыдущих:

1. **Устройство не открывалось ни разу.** Взято `Data Type Examples.8 Bit
   Device` — до этого я работал только с `Simulation Examples.Functions`,
   `Data Type Examples.16 Bit Device` и `Channel1.Device1`.
2. **В референсе нет типов.** Столбец `Data Type` убран намеренно. Генератор
   обязан определить типы обходом сервера, иначе задача не решается.
3. **Источник истины — сервер, а не код скилла.** Значения сначала записаны
   на сам OPC UA сервер командой `opcuactl write value`, и только потом
   сравнивались с тем, что прочитала точка WinCC OA. Ни одно из этих чисел не
   участвует в генераторе, поэтому ошибка в таблице типов проявилась бы
   расхождением, а не совпадением.

## Значения подобраны как ловушки

| Канал | Значение | Что должно было сломаться |
| --- | --- | --- |
| `Word1` | 60000 | выше 32767: `DPEL_INT` дал бы отрицательное |
| `DWord1` | 4000000000 | выше предела int32 |
| `LLong1` | −9007199254740993 | за пределами 2⁵³: через double получилось бы −9007199254740992 |
| `QWord1` | 18000000000000000000 | выше предела int64, знаковое чтение ушло бы в минус |
| `Char1` | −100 | `SByte` в `DPEL_UINT` дал бы 156 |
| `Byte1` | 200 | `Byte` в знаковом элементе дал бы −56 |

## Что сделал генератор

Типы определены обходом сервера, без участия референса:

```
Boolean   751  DPEL_BOOL
Byte      753  DPEL_UINT
SByte     752  DPEL_INT
Int16     754  DPEL_INT
UInt16    755  DPEL_UINT
Int32     756  DPEL_INT
UInt32    757  DPEL_UINT
Int64     758  DPEL_LONG
UInt64    759  DPEL_ULONG
Float     760  DPEL_FLOAT
Double    761  DPEL_FLOAT
String    762  DPEL_STRING
Направления: 7
```

Все 12 значений прочитаны точно. Расхождений ноль.

| Канал | На сервере | В точке OA | |
| --- | --- | --- | --- |
| `Boolean1` | true | TRUE | совпало |
| `Short1` | −20000 | −20000 | совпало |
| `Word1` | 60000 | 60000 | совпало |
| `Long1` | −1234567 | −1234567 | совпало |
| `DWord1` | 4000000000 | 4000000000 | совпало |
| `LLong1` | −9007199254740993 | −9007199254740993 | совпало |
| `QWord1` | 18000000000000000000 | 18000000000000000000 | совпало |
| `Float1` | 3,5 | 3,5 | совпало |
| `Double1` | 2,718281828 | 2,718281828 | совпало |
| `String1` | `PRIVET-42` | `PRIVET-42` | совпало |
| `Byte1` | 0 | 0 | совпало, см. ниже |
| `Char1` | 0 | 0 | совпало, см. ниже |

Прогон: `PASS=16  FAIL=0`, все 12 элементов `quality = 128`.

`LLong1` стоит отдельного внимания. −9007199254740993 не представим в
double: ближайшее значение — −9007199254740992. Значение пришло без
потери, значит путь действительно 64-битный целочисленный, а не через
вещественное число.

## Восемь бит: тест в обратную сторону

`Byte1` и `Char1` подготовить заранее не удалось. У `opcuactl write value`
нет типов `byte` и `sbyte` в списке поддерживаемых, а запись через `int16`
сервер отвергнул с `BadTypeMismatch`, код `2155085824`.

Поэтому эти два канала проверены в обратную сторону: значение записано из
WinCC OA и подтверждено чтением с сервера.

| Канал | Записали из OA | На сервере | Тип на сервере |
| --- | --- | --- | --- |
| `Byte1` | 200 | **200** | `TypeIDByte` |
| `Char1` | −100 | **−100** | `TypeIDSByte` |

**Вывод: драйвер WinCC OA пишет 8-битные типы, хотя opcuactl не умеет.**
Инструмент не умеет — не значит, что протокол не поддерживается.

## Что эта проверка доказывает и что нет

**Доказывает:**

- определение типов обходом сервера работает без типов в референсе;
- таблица `OPCUATransformation` и выбор типа элемента верны для 12 типов,
  включая 64-битные и беззнаковые;
- направление 7 выбирается по `AccessLevel` правильно;
- формат адреса собирается правильно;
- значения не теряют разрядность и знак.

**Не доказывает:**

- **Задачи, где сервер неизвестен.** Прежде чем задавать значения, я
  сервер обследовал. Настоящая проверка «с нуля» — это когда модель не
  знает ни одного узла и должна найти нужный по запросу пользователя.
- **Стенды других версий.** Всё на CTL 3.18 и Kepware KEPServerEX V6.
- **Массивы.** Их в картах много, генератор не обрабатывает.
- **Определение `VARIANT_ID` и `ELEMENT_ID`.** Стоят `1$1`, причина не
  исследована.

## Ошибок пайплайн не выявил

Прогон прошёл с первого раза, расхождений ноль. Это законный результат, но
заметим честно: дефекты находились раньше на этапах, где я делал ручную
работу — разбор `wordOrder`, направление доступа, типы элементов. Как
только работа стала механической, дефекты кончились.

Это и есть содержательный вывод приёмки: **скилл полезен ровно настолько,
насколько механизирована задача.** Там, где нужен разбор и решения, ошибки
были. Там, где всё выводится по правилам, прошло чисто.
