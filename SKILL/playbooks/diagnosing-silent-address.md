# Адрес настроен, а данных нет

Самая частая задача на стенде и самая дорогая, потому что все её признаки
молчаливые: ошибок нет, точка создана, конфиг записался, значение равно нулю.

## Сначала отличить «нет данных» от «данные не меняются»

```
качество 128 и bad снят, значение не меняется  →  адрес работает, сигнал константа
bad = 1, значение 2147483647                   →  драйвер не смог прочитать
качество 128, значение 0, не меняется          →  читает, но читает мусор
значение приходит мусором                      →  неверный тип или порядок слов
```

Заглушка `2147483647` — это `INT32` максимум, WinCC OA ставит его при ошибке
чтения. Видеть его в 32-битном канале — признак, что канал не прочитан.

## Снять состояние

Один замер отвечает на большинство вопросов сразу:

```ctl
main()
{
  string e = "STP.Current_Temperature";
  dyn_anytype v; bool b; int q; time t;
  int rc = dpGet(e + ":_online.._value", v);
  dpGet(e + ":_online.._bad", b);
  dpGet(e + ":_online.._quality_code", q);
  dpGet(e + ":_online.._stime", t);
  DebugN("rc=", rc, " v=", v, " q=", q, " bad=", b, " stime=", t);
}
```

`_online.._stime` — время последнего обновления. Если оно не меняется, точка
не обновляется вовсе, и искать надо не значение, а причину молчания.

**Путь к элементу структуры — без завершающей точки.** `STP.CurTemp:_online.._value`.
Точка нужна только для корня одиночной точки: `ExampleDP_Arg1.:_online.._value`.
С точкой на элементе `dpGet` даёт `DP does not exist` и `rc = -1`.

## Проверить, что драйвер вообще видит точку

Узел подключения не назначен драйверу — самая частая причина, и снаружи её
не видно совсем.

```ctl
for (int k = 1; k <= 6; k++)
{
  string d = "_Mod_Plc_" + k;
  int drv; dpGet(d + ".DrvNumber", drv);
  int unit; dpGet(d + ".UnitAddress", unit);
  int act; dpGet(d + ".Active", act);
  int cs; dpGet(d + ".ConnState", cs);
  int err; dpGet(d + ".Error", err);
  string hp; dpGet(d + ".HostsAndPorts", hp);
  DebugN(d, ": Drv=", drv, " Unit=", unit, " Active=", act,
         " Conn=", cs, " Err=", err, " Hosts='", hp, "'");
}
```

| Признак | Значит |
| --- | --- |
| `DrvNumber = 0` | драйвер этот узел не опрашивает, остальное не важно |
| `UnitAddress = 0` | узел не настроен |
| `ConnState = 0` | соединение не установлено |
| `Error` не ноль | смотреть код в документации драйвера |

`DrvNumber` пишется из CTL, хотя остальные узлы обычно настраивают через
диалог:

```ctl
dpSetTimedWait(0, "_Mod_Plc_2.DrvNumber",     2);
dpSetTimedWait(0, "_Mod_Plc_2.UnitAddress",   2);
dpSetTimedWait(0, "_Mod_Plc_2.HostsAndPorts", "192.168.0.107:504");
dpSetTimedWait(0, "_Mod_Plc_2.Active",        TRUE);
```

После этого драйвер подхватывает узел сам, перезапуск не нужен. На стенде
проверено: все шесть узлов подхватились сразу после записи.

`dpGetAllAttributes` на узле `_Mod_Plc_N` возвращает пусто — узел не обычная
точка данных, перечислять нечем. Список полей известен: `DrvNumber`,
`PlcNumber`, `UnitAddress`, `Active`, `HostsAndPorts`, `ConnState`, `Error`,
`SentFrames`, `RcvFrames`, `RejFrames`.

Счётчики `SentFrames` и `RcvFrames` полезны: если отправлено много, а
получено ноль, запросы уходят, а ответы не приходят.

## Проверить адрес элемента

Сравни с рабочей точкой того же типа, а не с эталоном из другого устройства.

```ctl
string ref;  dpGet("STP.Current_Temperature:_address.._reference", ref);
string id;   dpGet("STP.Current_Temperature:_address.._drv_ident", id);
int    dt;   dpGet("STP.Current_Temperature:_address.._datatype", dt);
int    dir;  dpGet("STP.Current_Temperature:_address.._direction", dir);
string grp;  dpGet("STP.Current_Temperature:_address.._poll_group", grp);
int    act;  dpGet("STP.Current_Temperature:_address.._active", act);
DebugN("ref='", ref, "' id='", id, "' datatype=", dt,
       " direction=", dir, " группа='", grp, "' active=", act);
```

Обязательный набор, без любого из этих адрес молча не работает:

| Атрибут | Правильное значение |
| --- | --- |
| `_distrib.._type` | `DPCONFIG_DISTRIBUTION_INFO` |
| `_distrib.._driver` | номер драйвера |
| `_address.._type` | `DPCONFIG_PERIPH_ADDR_MAIN` |
| `_address.._reference` | `M.<PLC>.<FC>.<регистр>` |
| `_address.._active` | `TRUE` |
| `_address.._drv_ident` | строка `"MODBUS"`, не число |
| `_address.._datatype` | 561, 563, 564, 566 или 567 |
| `_address.._direction` | 4 опрос, 7 вход-выход |
| `_address.._poll_group` | существующая группа, например `System1:_1s` |

Чего в рабочем конфиге **нет**: `_address.._value` и `_address.._mode`.
Запись в `_value` даёт `DP does not exist`.

## Группа опроса

Ищется в проекте, а не придумывается. Без неё адрес не опрашивается.

```ctl
string findPollGroup()
{
  dyn_string all = dpNames("_**");
  for (int i = 1; i <= dynlen(all); i++)
  { if (dpTypeName(all[i] + ".") == "_PollGroup") { return all[i]; } }
  return "";
}
```

`dpNames` возвращает имена уже с системным префиксом, то есть `System1:_1s`.
Если ничего не найдено, группу надо создать через панель системы, Drivers,
Poll groups: у точки типа `_PollGroup` нет атрибутов опроса, писать нечего.

## Если точка не в системе пользователя

`dpGet` на элемент отсутствующей точки даёт `DP does not exist` и `rc = -1`.
При этом значение переменной остаётся прежним, то есть нулевым, — и легко
принять за «данные не пришли».

## Сверка с эмулятором

Если эмулятор Modbus запущен, его журнал — независимый источник правды:
драйвер пишет каждый запрос, а адрес не опрашиваемый не пишет ничего.

```
[14:32:43] read   slave 1: FC1 coils 0..5
[14:32:43] read   slave 1: FC2 input 0..15
[14:32:43] read   slave 1: FC3 holding 0..19
[14:32:43] read   slave 1: FC4 ireg 0..11
```

Запросов нет — проблема в конфигурации точки. Запросы есть, а значения
мусорные — проблема в типе или порядке слов.

## Порядок слов

Самая дорогая находка. Драйвер WinCC OA 3.18 на стенде читает **`CDAB`**,
младшее слово первым.

С `ABCD` все float-значения приходят перевёрнутыми, и ошибки не сообщается:

| Канал | `ABCD` | `CDAB` |
| --- | --- | --- |
| `Firmware_Version` | −4.95e+32 | **3.14** |
| `Energy_Consumption` | −2.36e−20 | **141.83** |
| `Total_Operating_Hours` | `bad = 1` | **40620** |
| `Serial_Number` | 2040745579 | **987654321** |

Порядок слов задаётся в карте эмулятора, а не в точке: скрипт про него не
знает ничего. Если значения приходят неверно, а адрес точно верный, сначала
проверяй порядок слов.

## Мусор от неверного `count`

Если в карте запись занимает один регистр, а точка объявлена как `FLOAT` на два
регистра, канал съест следующий сигнал, и оба придут битыми.

`4.13e-39` в температуре означает ровно это: целые значения, прочитанные как
float.

`count` в карте и `_datatype` в точке обязаны совпадать. Проверяй построчно
до привязки, а не после того, как значения пришли неверными.

## Порядок диагностики

1. `_stime` обновляется? Нет — ищем, почему молчит драйвер.
2. Узел привязан к драйверу? `DrvNumber` не ноль?
3. Есть ли запросы в журнале эмулятора? Нет — конфиг точки.
4. `quality = 128` и `bad` снят? Нет — читается, но с ошибкой.
5. Значение осмысленное? Нет — тип или порядок слов.
6. Значение меняется? Нет — по референсу это константа, и доказать работу
   нечем. Спроси пользователя.

## Чего не делать

- Не перезапускай драйвер, пока не проверил `DrvNumber`. Перезапуск на
  непривязанный узел ничего не даёт, но стоит времени.
- Не бери эталон из другого устройства. Адрес `M.1.3.0` рабочий для одного
  устройства и бессмысленный для другого.
- Не проверяй «пришло ли значение», спрашивая пользователя, должно ли оно
  меняться. Сначала сними два среза сам.
